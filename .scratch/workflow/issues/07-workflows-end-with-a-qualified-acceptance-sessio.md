# 07: Workflows end with a qualified acceptance session instead of waking main

**Status:** needs-triage
**Owner try:** no
**Blocked by:** 05, 06

**What to build:** Spec §2.1 (D-2026-11-25-07): main is the owner's discussion session and is decoupled from runs. A `handback` step goes by default to a qualified acceptance session, not main: a new shipped role `lead` (`packages/hud-mcp/roles/lead.json` + `instructions/lead.md`): a fresh Claude Code tab session on `claude-opus-5-5` at thinking high with the HUD MCP tools, i.e. the same model and powers as the main session (owner 2026-11-25). Owner: this is project-lead acceptance like the main session does today, NOT code review — code review stays with the independent `reviewer` role per the convention, and templates run it as a declared step where the convention calls for one (milestone review, process-killing code, installer, owner config); the lead acts on its findings. The lead receives the run's report refs, the declared choices and the acceptance criteria, decides one branch (finish / repair / continue) with reasons via its report, and its session is closed through herdr when it answers (normal HUD closure). Items the acceptance session is unsure of but that do not block (doubts, follow-ups, possible defects below the bar) go to `Todo:` lines in its report; the runner stores them on the run record, the end notice states the count, and `hud_read({job: <run>})` lists them for main to take to the owner later — they never wake main or stop the run (owner 2026-11-25: tickets are a clear dependency path suited to automatic progress; same-model acceptance keeps behaviour consistent; uncertain items go to todo; this cuts main's tool calls). It may escalate to main only for owner matters that block (scope, value trade-off, visible deletion, irreversible act) — an `escalate` choice that pauses the run and wakes main once. `to: "main"` stays available per step. The shipped ticket-queue template gains a closing acceptance step: after the last ticket lands, the lead accepts the feature as main does today: reads the reports and checks, tries it live where the brief or ticket says how, reads the milestone `reviewer` report — the template runs the independent reviewer (two-axis review per `docs/delegation.md` step 5) as a step before the final lead, so the lead never waits on it — and judges its findings, then finishes, or adds repair tickets and continues the queue (bounded: at most 2 repair rounds, then escalate). Owner 2026-11-25: a run is an independent work stream that never depends on the main session being alive; main only looks in. Test-version policy (owner 2026-11-25): the aim is that jobs in a run rarely ask and are sure of their task. (a) Before a run starts, a deterministic ticket check refuses to start and lists gaps when a ticket lacks a goal (`What to build`), acceptance items, valid `Blocked by` references, or a line saying how to try the result (or an explicit `Live try: none`). (b) Jobs in a run get a brief line: proceed on the ticket, spec and your own default; write each assumption as an `Assumed:` line (the runner moves these to the run's todo); ask only when no reasonable default is safe; report owner matters (scope, value trade-off, visible deletion, irreversible act) as `Blockers:`, which pauses the run without a wake. (c) Assumption breaker: a job report with more than three `Assumed:` lines, or one marked as about scope, pauses the run like a failed pilot (one notice on the run, no main wake). (d) A question that is asked goes to a temporary lead started for that question (questions within a short window may share one) — the important fallback; never to main and never to a resident lead. Ask-disabled jobs and hand-backs to `main` remain protocol options any template may choose (the engine is a free composition engine; defaults are template policy). A lead lives for ONE decision: the runner builds a compact packet from the run record (goal, declared choices, report/check/review refs, prior decisions and todo), starts the lead, takes its answer, and closes it; no lead stays alive between decisions (owner 2026-11-25: a long-lived lead would only move main into the workflow). The run record is the run's memory. Main receives only the one end notice (with the acceptance verdict line) and escalations. The lead job runs outside the batch/role cap reservations like scouts; it is cheap-class. The lead never lands outside its run's declared branches and never edits `docs/spec.md`.
