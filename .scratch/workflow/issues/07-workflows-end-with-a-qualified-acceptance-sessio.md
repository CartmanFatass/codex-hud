# 07: Workflows end with a qualified acceptance session instead of waking main

**Status:** ready-for-agent
**Owner try:** no
**Blocked by:** 05, 06

**What to build:** Spec §2.1 (D-2026-11-25-07): main is the owner's discussion session and is decoupled from runs. A `handback` step goes by default to a qualified acceptance session, not main: a new shipped role `lead` (`packages/hud-mcp/roles/lead.json` + `instructions/lead.md`): a fresh Claude Code tab session on `claude-opus-5-5` at thinking high with the HUD MCP tools, i.e. the same model and powers as the main session (owner 2026-11-25). Owner: this is project-lead acceptance like the main session does today, NOT code review — code review stays with the independent `reviewer` role per the convention, and the lead dispatches it where the convention calls for one (milestone review, process-killing code, installer, owner config) and acts on its findings. The lead receives the run's report refs, the declared choices and the acceptance criteria, decides one branch (finish / repair / continue) with reasons via its report, and its session is closed through herdr when it answers (normal HUD closure). Items the acceptance session is unsure of but that do not block (doubts, follow-ups, possible defects below the bar) go to `Todo:` lines in its report; the runner stores them on the run record, the end notice states the count, and `hud_read({job: <run>})` lists them for main to take to the owner later — they never wake main or stop the run (owner 2026-11-25: tickets are a clear dependency path suited to automatic progress; same-model acceptance keeps behaviour consistent; uncertain items go to todo; this cuts main's tool calls). It may escalate to main only for owner matters that block (scope, value trade-off, visible deletion, irreversible act) — an `escalate` choice that pauses the run and wakes main once. `to: "main"` stays available per step. The shipped ticket-queue template gains a closing acceptance step: after the last ticket lands, the lead accepts the feature as main does today: reads the reports and checks, tries it live where the brief or ticket says how, dispatches the milestone `reviewer` (two-axis review per `docs/delegation.md` step 5) and judges its findings, then finishes, or adds repair tickets and continues the queue (bounded: at most 2 repair rounds, then escalate). Main receives only the one end notice (with the acceptance verdict line) and escalations. The lead job runs outside the batch/role cap reservations like scouts; it is cheap-class. The lead never lands outside its run's declared branches and never edits `docs/spec.md`.
