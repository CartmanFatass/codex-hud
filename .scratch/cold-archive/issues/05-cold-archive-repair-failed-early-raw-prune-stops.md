# 05: Cold archive repair: failed early raw prune stops retrying on unrelated refreshes, rejected Sonic session is raw, queue run dirs archive whole or keep the receipt

**Status:** ready-for-agent
**Live try:** none
**Blocked by:** 04

**What to build:** Repair from milestone review jaa2c92319593669d (findings 1-3) of cold-archive/01-04 (spec §2.3, D-2026-11-26-11: every prune path is move-then-delete; a failed archive write keeps the source; watcher cost stays as today; raw members are the only ones the cap may delete). (a) Failed early raw-log prune retries on every unrelated refresh: src/runtime/watch-runtime.ts:1198 calls pruneJobLogs (src/runtime/work-retention.ts:85-121) on every scan before the failed-retention gate, and pruneJobLogs returns false both for 'nothing to prune' and for an archive write failure. With an unwritable or full archive, each STATUS.json update of any other job re-enumerates the cold store and synchronously recompresses a large stdout just to fail again. Make pruneJobLogs distinguish failure from no work and gate its retry the same way as full retention: retry only on a housekeeping pass or after that job's own inputs change, never on unrelated refreshes; keep the source logs on failure. Preferred (the review's deletion suggestion): replace the recursive retentionInputStamp tree walk (watch-runtime.ts:470-509) with a failed-job set that is retried on housekeeping or marked dirty by that job's own watcher events, so a stuck job costs no tree walk on unrelated updates; drop the duplicated flow-name regexes it needs. (b) Rejected Sonic session escapes the raw cap: src/mcp/sonic-process.ts:167-174 renames a rejected continuation to `sonic-session.jsonl.rejected`, but isRawJobPath (src/roles/cold-archive.ts:97-105) only matches the unsuffixed name, so the transcript lands in the permanent text member and survives `retention.coldRawCapGB: 0`. Classify that writer-produced name (and any other suffixed copy of a session file HUD writes) as raw. (c) Queue run dir partly archived, then stranded: src/runtime/work-retention.ts:263-295 accepts only `handback-j<hex>` notice markers in a q* run directory, but pane-less ticket queues emit `handback-perm-<16 hex>` keys (src/mcp/ticket-queue-step.ts:73-90, PERMISSION_ID in src/mcp/worker-permissions.ts:24) whose `.noticed`/`.observed` files live beside `graph.json`. One such marker makes collection skip every subdirectory file, yet the receipt is still archived and unlinked, so `hud archive extract <q-id>` cannot restore graph.json and nothing triggers another sweep. Recognise the real notice-key grammar (derive it from the code that writes the keys rather than a third hand-written regex), use one predicate for both collection and cleanup, and keep the receipt (and its run dir) when the run directory could not be collected in full. No new dependency; files 0600, dirs 0700; watcher refresh still does zero cold-archive I/O.

- [ ] With raw publication blocked, a closed job with a report and retained unchanged stdout.jsonl gets zero pruneJobLogs archive attempts (no cold-store reads or writes) while a separate active job's STATUS.json updates and the watcher rescans; the stdout stays; the prune succeeds on a housekeeping pass or after that job's own inputs change once the archive is writable.
- [ ] A job whose `sonic-session.jsonl.rejected` exists archives it into the raw member, not the text member; `hud archive extract` restores it byte-identically while raw is present, and after raw eviction (coldRawCapGB 0) it is absent from the text member.
- [ ] A terminal pane-less queue with graph.json and a `handback-perm-<hex>.noticed` marker archives graph.json and the marker into its `<q-id>.text` member before the receipt and run dir are removed; `hud archive extract <q-id>` restores graph.json. When the run dir holds a file retention cannot collect, the receipt and run dir both stay for the next sweep.
