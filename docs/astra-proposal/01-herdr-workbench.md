# Astra Proposal 01 · 让 MyHUD 能直接操作 agent 的工作现场

2026-11-25 · 产品探索提案 · 调研基线为 MyHUD `3b20ba1d`、herdr-hud `0409f9fa`。下文的优先级用于挑选原型，尚未排期。

**建议先做「选中一段输出，问另一个窗格」，再做「打开成果，直接试一下」。** 前者值得做成 fork 的第一个演示：左边 Codex 刚跑挂测试，框住两行报错，点右边正在改代码的 Claude，问“这和你刚改的分支有关吗？”十分钟后还能从原摘录找到回答。后者更可能成为每天都用的功能：一个结果需要我判断时，按下回车就落在能复现它的现场。

这两个动作分别检验两件事：终端能否替人带上准确的上下文，MyHUD 能否替人省掉验收前找分支、拼命令、切窗格的时间。它们可以独立交付。

## 1. 已经具备哪些条件

上游 herdr 已有终端托管、窗格、插件和 socket API。本次以本地 fork 的源码判断具体接口。下表中 Rust 路径相对 herdr-hud 仓库。MyHUD 的任务、派发和交付语义以当前产品规格为准。[herdr 上游](https://github.com/herdrdev/herdr) · [MyHUD 产品规格](../spec.md) · [MyHUD 消息和交付接口](../../packages/hud-mcp/README.md)

| 能力 | 查到的实现 | 对提案的影响 |
| --- | --- | --- |
| 取得用户框选的文字 | `src/app/custom_commands.rs` 的插件快捷键分支会核对来源 pane，再把 `selected_text` 传给动作。`src/app/api/panes.rs` 的 `pane_selection_text` 支持按内容版本读取，读取前后都检查变化 | 第一版可以从插件动作起步。活跃窗格持续刷屏时可能返回 `stale_content`，应让用户看见实际将要发送的摘录 |
| 在现有画面旁做交互 | fork 的 `docs/next/website/src/content/docs/plugins.mdx` 支持 overlay、popup、split 等放置方式。popup 是会话级单例，Copy mode 或其他模态界面占用时可能返回 `ui_busy` | 先取出选区，再开目标选择器。若打开失败，保住草稿。临时顾问的后台任务寿命由 MyHUD 管，关闭弹窗只收起视图 |
| 把文字送到正确的 worker | fork 的 `HUD-FORK.md` 记录 tab 的 `launch_id` 和 direct-exec 的进程身份。MyHUD 的 `hud_send` 支持 `message_key`；单 job 发送在特定状态下会续工或创建 repair，多目标形式只发给 working jobs | 候选目标显示 job 和角色；提交时再校验身份。可优先试 `jobs: [目标]` 的仅工作中投递语义，过期目标显示已结束，避免一次提问意外重开工作 |
| 把同一件事摆成平铺工作台 | `src/app/api/layouts.rs` 的 `handle_layout_export` 导出布局，`handle_layout_apply` 根据描述创建 tab 和 pane，可替换目标 tab | 新开的验收台、启动模板都有入口。给**正在跑的同一组进程**换布局，需要保留 PTY 身份的重排机制，不能直接套用模板 |
| 打开已有成果 | MyHUD 已有 Objective、显式 owner request、证据链接、managed worktree 和 landing。普通 worker 问题由主会话处理 | 「试一下」可挂到一条明确要求人判断的结果上。关闭预览、给反馈、接受 Objective、合入代码是四个独立动作。[Objective 与请求](../spec.md) |

**验证深度。** 在临时 HOME、HUD_HOME 和 socket 路径下，用本地已有的 herdr 测试二进制重跑了三个鼠标选区用例，均通过：释放鼠标时取最新位置、调整窗口大小时取消未完成的取词、内容更新时保留仍有效的范围。用例位于 `src/client/shell/tests/mouse_selection.rs`。这给选区交互提供了依据；插件到真实 agent 的往返、回答关联和回放开销仍需原型验证。另有一个已记录的 live-handoff 身份问题，本次把跨 handoff 锚定列为待验证能力。[fork 问题 07](../../.scratch/herdr-fork/issues/07-fork-live-handoff-keeps-a-direct-exec-pane-s-ide.md)

## 2. 首个演示：让一段报错可以被提问

1. **选中。** 测试窗格出现合成报错 `expected 2 rows, got 3`。用户选中它，从插件动作打开「问另一个窗格」。第一版让 `@` 做选择器内的交互，普通终端里的 `@` 仍可自由输入。
2. **提问。** 选择器列出本项目可接收消息的工作中 job，展示角色、工作目录和本次摘录。用户选定接收者，只写“哪个改动会多出一行？”即使源窗格随后刷新，待发送内容也保持可见。
3. **回来。** 来源旁保留一条“已排队”的提问。MyHUD 给这次提问分配关联 ID，由接收端适配器或约定的结构化回报带回同一 ID。找到匹配才显示“已回答”。worker 普通日志和整份结束报告都不足以证明它答了这一个问题。
4. **原处消失时。** 能核实来源身份和内容位置时，在原处显示引用。全屏 TUI 重绘、窗口变窄或原 tab 已关闭时，回答退回到带原文的摘录卡。用户仍能看懂“当时问的是哪一段”。两个窗格里碰巧出现同一句错误，不足以重新定位。

**最小原型。** 选区读取、目标选择、把摘录送到一个工作中 job，先用插件和 HUD 消息通道串起来；第一版回答先回摘录卡。herdr 负责用户看见的选区和焦点，MyHUD 负责 job 身份、投递状态和回信。只有在用户确实会回看原处以后，再给 fork 加随内容移动的批注绘制。来源可以是普通测试 shell，接收端首轮限定为 HUD 能识别的 worker；任意两个独立主会话互发消息另行试验。

**原型过关条件。** 在临时工作区开一个测试 pane 和两个能分别回报 A、B 的模拟 worker。分别选择相同报错，交叉发问、反序回信，并在途中切焦点、关闭目标、重试一次。验收者应能找到每个回答对应的原文，发送端能区分排队、已回答、目标已结束和投递结果未知。然后用一组真实 CLI 验证忙碌时的接收和回报；若回报关联不可靠，先交付「引用并发送」，保留人工回到目标窗格的入口。

## 3. 最值得日用：按一下就能验收

设想有人改了 MyHUD 的窄屏状态栏。主会话发来一条结果：“请判断 60 列时等待提示是否清楚。”打开后直接看到同一份合成状态在 40、60、120 列下的渲染。点中 60 列的截断处写一句“右侧还要留出 job 数量”，反馈随结果回到负责的会话。用户省掉的是复现环境的准备时间。

第一版给显式 owner request 附一份小型预览描述：**要判断的问题、对应提交、已有产物或本地受信预览动作、反馈去向**。MyHUD 解析请求和产物，herdr 打开已有文件或新预览 tab。优先使用可独立打开的产物；若依赖临时 worktree，则在打开时核对路径和版本。目录已回收时仍展示现存证据及缺少的条件。项目提交的描述只能引用用户配置过的动作，避免打开一个结果就执行仓库提供的任意命令。

**第一轮可直接用 MyHUD 验收自己。** 做一份三宽度预览，再分别从活跃 worktree、已清理 worktree、过期提交打开它。观察用户能否在一次打开后开始判断；若仍要自己定位分支或补跑命令，记录具体缺口。相比既有的 worktree 交付提案，这里关心的是人能否复现并判断交互效果。[既有 worktree 交付提案](../neon-proposal/24-worktree-delivery-loop.md)

## 4. 其余想法，各自先碰哪块硬骨头

| 想法 | 第一版怎么玩 | 可行性与最值得验证的缺口 |
| --- | --- | --- |
| 窗格批注 | 给一段输出留一句“下轮看这个” | 摘录式可先做。跨重绘定位及“下轮”的可靠时机要分别验证 |
| 临时顾问 | 框住 diff，按键打开只讨论这段的侧窗 | 可复用插件视图和显式 job 创建。先试收起后找回答、连续开两次和取消任务 |
| 把窗格拖给同事 | 从测试 pane 拖到 worker 上，弹出「调查这个失败」 | 菜单版可复用选区投递。拖拽版需定义快捷修饰键，与选择文本、调整分隔线、应用接管鼠标共存 |
| 带现场的问题 | 从请求跳到配置对照，答完回原处 | 焦点和 tab 可先恢复。输入草稿属于 CLI，宜保留原进程并由其自行维持；需实测切换期间发生重绘的情况 |
| 工作区缩放 | 从项目缩到待决事项，再放大到对应 pane | 先用已有状态做只读总览。多窗格实时缩略图需量渲染成本；headless job 直接打开报告 |
| 「我离开以后」 | 从手动书签开始，依次看新结果和未决问题 | 可从已有 Objective、请求和结果记录派生。测试变绿需有测试结果证据，“推翻假设”需 worker 主动记录 |
| 工作姿势 | 一键切到写代码、对照或验收布局 | 新台模板可先做。存活进程的重排用持续计数的子进程验证，来回切换后检查进程身份、计数和焦点 |
| 同一窗格两个视角 | 左边冻结报错摘录，右边继续刷日志 | 文本快照可先做。两个可独立滚动、改变宽度的实时视图共用一个 PTY 尺寸，须设计谁控制应用尺寸 |
| 双路线分叉与盲评 | 同一需求开两个隔离 worktree，把产物匿名排成左右两栏 | 创建与比较可拆开交付。先用相同输入夹具重跑；同步广播任意按键容易因焦点和页面状态不同而失真 |
| 换模型接手 | 一张可删改的交接卡带上目标、提交、失败命令 | 适合原型。原 worker 和接手者同时写同一 worktree 会相互干扰，需要显式移交或另开 worktree |
| reviewer 布置现场 | 回报里附上基线、改动、失败输出三处入口 | 复用验收描述和新布局。先试其中一个证据缺失时，余下两处是否仍可打开 |
| 录制常用动作 | 把开 worktree、起角色、开日志存成带参数的动作 | 先记录结构化操作。首次只支持可预览的少数命令，重跑前能看见将创建哪些资源 |
| 项目自带视图 | MyHUD 仓库提供状态栏试衣间 | 插件 pane 已能承载 TUI。先做一个由用户启用的项目视图，观察哪些数据接口值得稳定下来 |
| 十秒 TUI 回放 | 按键保存刚刚发生的错位，逐帧看尺寸和焦点 | 研究型。先录合成 TUI 的渲染帧、尺寸和焦点，用内存环形缓冲量开销；含真实输入的持久化要单独决定 |

## 5. 怎样决定还值不值得往下做

- **先跑通半分钟演示。** 合成 worker 验证不会串回复，真实 worker 验证忙时投递。一次演示里用户只需选中、挑人、写问题。若最耗时的是等目标空闲，下一步优先改善排队反馈。
- **再拿一次真实改动做验收。** 选一个本来就需要 owner 亲手试的 TUI 改动。记下从打开请求到第一次有效操作，中间还要切几次 tab、找几次路径。这比统计点了多少次「试一下」更能决定是否值得推广。
- **给 fork 留一个独立实验。** 如果先选技术探索，我会选十秒回放：用同一个合成 TUI 连续高速刷屏和 resize，对比启用前后的内存、输入延迟，以及回放能否看清错位的第一帧。它即使最终只成为 MyHUD 自己的调试工具，也有清楚的用途。

第一项适合展示自有 fork 能带来的交互，第二项直接服务项目已经承担的验收工作。两条路线都跑过一次，再决定要给 herdr 增加长期维护的锚点、视图协议还是录制能力。
