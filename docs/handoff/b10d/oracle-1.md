The owner-approved worker route and all qualification gates remain binding. The choices below are implementation decisions within B10D's existing ownership. They do not authorize changes to B12, B16, B17, renderers, dependencies, build configuration, contracts, or the supported-profile limits. 1. **Choose admission before the legacy slice, with completion-triggered consumption of an already pending cadence request.**

Use two distinct clocks: oldest request enqueue time for end-to-end latency, and one read-work deadline allocated when that logical operation actually becomes active. A pending request has identity, scope, latest requested inputs, and its original enqueue time, but no allocated reader budget or read deadline. This avoids giving an already expired 40 ms read deadline to a request that legitimately waited behind another operation. Queue waiting is still fully included in the operation gate; it is never forgiven by activation.

The concrete protocol is:

- On a normal collection opportunity, enqueue or coalesce one request. Replacing pending inputs preserves the oldest enqueue time and retains superseded/incomplete accounting. Watcher hints only invalidate/coalesce existing work; result paints, key presses, resize, and clock paints do not create collection opportunities.
- If the client is idle and there is no unconsumed result, admit this request once. Its shared cooperative deadline starts before the admitted main collection slice. Preserve the existing 40 ms read-work envelope, with the legacy root limited to 4 MiB, 2,000 records and at most 20 ms of remaining time. Claim/consume this legacy grant exactly once through a token tied to that request and scope. Pass actual legacy charges, remaining shared deadline, and request identity to the worker. A thrown read without usable statistics conservatively consumes its grant; do not silently charge zero.
- Worker native/recovery work receives the existing maximum 4 MiB/2,000-record/20 ms grant within that same deadline. Worker work and legacy work together must remain within 8 MiB; do not turn either half into an independent 8 MiB allowance, and do not enlarge the one native grant by donating an unused legacy half. Existing recovery reservations remain inside the worker slice, with the B12M accounting limitation reported explicitly.
- If the worker is active or its result is awaiting consumption, a normal opportunity may update the one pending request but gets no legacy root grant. Use compatible cached legacy data. Do not leave an earlier parse budget/token installed for watcher callbacks to reuse.
- On a result, validate identity and payload, adopt the complete compatible view, run the immediate result paint using cached main-thread collection data and current display clocks, and enqueue the frame. Then acknowledge that result. This handler does not run a root parse or another ordinary HUD collection.
- After that acknowledgement, the client may activate the already pending cadence request immediately. This consumes a previously recorded opportunity; it is not a new collection loop. Allocate its shared deadline at this activation, give it a worker slice of at most 4 MiB, and assign zero legacy allowance/charges. It must retain the old enqueue timestamp. If no pending request exists, stop. Continuation, completion, or an ACK alone never manufactures another request.
- An ACK followed by a request on the same ordered worker message channel is sufficient if the worker validates the ACK's incarnation/request/result identity and cannot start another publication while its result slot is occupied. It may also use one combined consume-and-dispatch message. Neither form adds a queue.

The next normal opportunity may again admit a legacy slice when idle; while busy it only coalesces. Thus a ready local commit is painted without a 1/5-second polling delay and without a legacy parse blocking adoption. Do not choose either alternative from the question: waiting for the next cadence unnecessarily delays already requested progress, and parsing the root in the result handler puts avoidable collection work on the commit-to-paint path.

Keep one active-operation slot occupied through result consumption, even after worker computation has finished. Retain operation records for expired deadlines, busy, failed, continued and superseded work. A read deadline exhausted by IPC/legacy delay is an incomplete/deferred read, not permission to reset the deadline; existing mandatory completion/publication work and synchronous overruns remain measured. A newly activated pending request is the only case above that allocates a new read deadline, because it never had one.

Gate legacy parsing on the existence of the participating worker client, not on whether a non-null delegation view has arrived. Initializing, failed and unavailable workers otherwise accidentally reopen the unrestricted legacy parsing path. Scope changes invalidate grant tokens and incompatible cached root/view data immediately. The no-client legacy route and short-lived entries remain their existing zero-worker paths.

2. **Choose conservative residency slots and demand-driven recovery; do not retain hidden reader state behind an evicted handle.**

Before opening a seventeenth reader, or retaining a new per-session recovery/checkpoint state that can keep reader runtime alive, reserve a residency slot. One session consumes one slot even if it has several of these objects. For this implementation, count a reader, incomplete recovery/parser state, captured ReaderResult, or prepared token/handoff retaining native state as resident. A detached committed projection plus bounded scheduling/topology metadata does not consume a reader slot, but still counts toward memory limits. This conservative accounting is an implementation choice under the approved limit, not a new allowance.

Eviction requires an affirmative, settled, recoverable accepted boundary, not merely caughtUp=true. At minimum:

- No active read, unacknowledged reader candidate, publisher pending candidate, unresolved publication outcome, active reset, or unfinished recovery/continuation can be discarded.
- The latest captured boundary must have been durably accepted by this publisher, including its recovery ACK. Compare the accepted checkpoint identity/boundary and source/run/binding context; offset or generation equality alone is insufficient. A historical resetReason in an already accepted, recoverable checkpoint is not by itself an active reset.
- Require no retained partial tail/discard state. Check generic parserState.pendingBytes, tailBytesSeen, tailAtEof, discardingOversize and discardOffset, and the corresponding Claude tailBytesSeen, tailAtEof and discardOffset. Unknown metadata cannot prove quiescence. A fixed-EOF partial record can have no continuation and caughtUp=true; it stays pinned. Oversized-record discard progress stays pinned until its safe boundary is reached.
- Exact IDs, accepted open calls, continuity and notice baselines must be durably recoverable. Dropping an accepted cache is allowed; deleting semantic state to fit the cache is not. Never use trimming, invented checkpoints, or an inferred baseline as eviction.

Drop all strong references to the evicted reader runtime: reader, captured result, prepared token/sources, checkpoint/recovery handoff, and any other closure retaining those objects. Keep committed display/evidence/topology metadata only where it is bounded and contains no such runtime handle. Retain the same SessionPublisher/StatusWriter, acquiring store and valid lease, its accepted ObservationProjection/notice baseline, and small accepted-context/scheduling metadata. Do not clone authority, create a new writer from a displayed summary, or call forget() merely for cache eviction.

This reset is within B10D ownership. SessionPublisher.discardReading() already drops result/prepared/sources/nativeMemory while preserving writer, lease and prior. Add an explicit quiescent-eviction guard/wrapper around that operation as needed; keep its authority/accepted-prior behavior. Clear obsolete preparation bookkeeping without advancing the accepted publication baseline. Seed later native continuity from the compatible accepted prior using the existing reader-status restoration logic, not stale speculative memory. If a context cannot be faithfully restored by the existing accepted reader/B16 path, that state is not evictable; a missing capability is an owner handoff, not a reconstruction shortcut.

Eviction sets a dormant recovery-needed flag, not dirty work by itself. Retain a bounded accepted publication-relevance token, source/run/binding identity, file signature and appropriate freshness metadata. Before the single read grant is planned, detect actual transcript/source/context changes or relevant ledger-fact changes for evicted sessions. Reuse the existing publication-key semantics (or a bounded token derived from those inputs), rather than introducing another status classifier. Do not make every global ledger high-water change dirty every evicted session. This pre-plan demand hook is necessary: current pending() can otherwise return null for caught-up dormant entries, while publishOne() skips !hasReading forever.

Freshness deadline expiry alone is paint-side freshness work. It does not make eviction a reason for age-only native rereads, renewal or publication. Any refresh demand must come from an existing actual observation requirement or changed relevant input. A genuine no-change population therefore remains zero-source-byte, even with more than 16 committed visible sessions. Recapture caused by a real ledger-only change is part of that changing population and all of its recovery/read cost is charged.

On actual selected demand, retain or obtain authority through the existing claim path; a follower does not open a publication reader. Recover the exact accepted head through B12, open/read the real adapter, then prepare a fresh captured reading before publication. Do not fabricate a ReaderResult from the display projection. If recovery uses the slice or leaves too little room for the maximum legal record, retain the recovered checkpoint/reader and its slot for the next fair grant. Never evict it between reconstruct-and-read steps. The next grant must accommodate the reader's declared minimum including LF/signatures, within the existing maximum. This is how to avoid a permanent reconstruct-and-yield loop.

If all 16 slots are pinned, do not allocate number 17. Preserve the blocked request's age and make resource-deferred coverage/health explicit while fair work on admitted continuations/publications proceeds. Resource-blocked sessions must not disappear from backlog/fairness accounting. When all pins are fixed incomplete EOF records and no legal progress frees a slot, that workload is resource-unqualified; do not promise fairness by hiding it from the ready set or discard a tail to manufacture room. No busy retry loop is introduced.

The 24 MiB external-buffer gate is separate from the reader count. A formula of 16 times MAX_RECORD_BYTES is not a complete bound: old/new partial buffers, rollback state, concatenation temporaries, read/signature buffers, encode/transfer copies, and the participating legacy parser can coexist; garbage collection need not immediately release discarded buffers. Reserve known worst-case work before admission/read/encoding and observe worker-local ArrayBuffer/external use plus the owned main-side buffers. Do not add external and arrayBuffers as though they were disjoint. Serialization and exact transfer-copy transients must be included, not only the final payload.

The current SessionReader API exposes read(), with no size/dispose/reservation contract. Therefore B10D can enforce the logical 16-slot limit exactly, but cannot claim that handle counting or occasional arrayBuffers samples prove a hard pre-allocation 24 MiB cap for every native temporary. Keep this limitation explicit. Qualification still requires evidence covering the actual supported profile and relevant peaks; a sampled estimate is not a waiver. If conservative reservations plus available evidence cannot establish the required resource result, report it unqualified and hand native allocation/disposal/telemetry changes to the reader/adapter owner. Do not edit those readers here or label the limitation solved by B12M. B12M separately owns exact SQLite/lazy-index read accounting.

3. **Choose node:v8 serialization of the validated plain-data view graph.**

The contract describes the payload's semantics, not a JSON wire syntax. A versioned envelope containing v8-serialized plain data is acceptable and is the smaller implementation choice here. Reference sharing between observation, lastObservation and detail.status may be preserved. No manual field compressor or new dependency is required. This is same-process transport between threads running the same Node binary, not a durable checkpoint format.

Validate the source as the actual DelegationViewModel DTO before encoding. Allow the DTO's supported scalar/array/plain-object values and shared references; reject functions, getters/setters, unexpected prototypes/classes, opaque authority objects, reader/checkpoint/recovery bodies, callable handles and unexpected collections/buffers. The codec alone does not enforce this: serializing a class can lose its prototype rather than reject it. Use shared-reference-aware validation so aliasing does not become duplicated work or an accidental rejection. Do not use a generic object dump of the collector.

Send an exact-sized standalone ArrayBuffer, not a Buffer's potentially larger backing pool. Transfer it once. Count the serialized Buffer and any exact-sized transfer copy while both exist. Validate protocol version, codec version, worker incarnation, scope epoch, request identity, monotonic view revision and byte length before decoding; then validate the decoded view/schema and compatibility before adoption. Preserve actual ledger observation time/boundary and each original observation stamp. Request IDs/revisions are transport identities, never observation sequence numbers.

An unchanged result is a small acknowledgement tied to the already adopted revision and current request. Object identity is a sufficient no-op optimization only where the view and its descendants are immutable and all separately transported semantic metadata are also unchanged. Timings/outcome/health still accompany the acknowledgement. A client without that base revision must request a complete result on an authorized opportunity; it cannot infer an initial view from an unchanged ACK.

Retain one adopted content version and at most one incoming result/view; release decoded/encoded predecessors promptly and do not keep a result history. A freshness projection may structurally share the adopted data, but must not create a history of full snapshots. Reuse the extracted pure freshness function and its captured deadlines on the paint side. Receipt, ACK, transport revision and a later local clock do not become new successful observation times. Scope-incompatible results are explicitly rejected/consumed and accounted for, never adopted under the current root.

Check the actual encoded payload against 2 MiB. Relations, report history and selection metadata are not guaranteed to fit merely because nodes are limited to 200. If it does not fit, send a small explicit transport/resource-failure outcome with request and accepted commit identity/outcome as applicable; retain the prior compatible view and mark that required display progress incomplete. Do not silently remove fields, truncate histories beyond existing public coverage rules, or call this a successful delivered view. Keep accepted notices/outcomes accounted for and durably recoverable; this failure is not latest-frame coalescing. The supported maximum fixture must fit to pass. If lossless graph encoding still cannot meet the bound, return the failed resource qualification for owner decision; do not introduce chunked delivery, a higher cap, or a new public-field policy here.

4. **Choose bounded owner shutdown and one replacement attempt on a later normal opportunity.**

close() immediately rejects new requests, invalidates the client epoch, and cancels pending dispatch. Ask the worker to settle the current operation and close its collector/stores, releasing valid leases best-effort. Start the 2-second waiting allowance when close is requested, including startup/operation/cleanup delay. On expiry, record dirty shutdown, issue terminate() best-effort, detach/unref the worker as appropriate, and return control to the owner's existing termination path. Do not then await the termination promise indefinitely or wait for a lease release. An unref alone is not proof of worker exit; actual exit is still required before any replacement.

A native stall may prevent the worker from processing the close message or finishing termination promptly. It does not authorize another worker. During normal life an error event without confirmed exit is likewise insufficient. After an unexpected actual exit, retain the compatible last view with degradation/freshness, record the unresolved operation, and allow at most one automatic replacement attempt on a later ordinary collection opportunity. A failed replacement startup consumes that allowance; there is no retry-until-success loop. Explicit owner shutdown never triggers replacement.

The replacement uses a new incarnation and fresh store authority. It reads/reconciles durable state before publication. An unexpired lease from the old worker is not transferable authority; normal follower/expiry handling applies. Preserve the distinction between transport ACK, durable reader ACK and durable commit. Missing result/ACK or termination does not prove rollback.

Private test-worker bootstrap injection is allowed for deterministic faults/stalls without adding production environment variables, CLI flags or a user-facing configuration. Keep it in the test harness/owned paths and make the production startup path unable to select it accidentally. Worker-local process.exit() tests thread death; owned child-process SIGKILL tests process death and orphan behavior. They are different cases and both retain real temporary HUD_HOME/SQLite state where applicable.

Existing isolated test techniques that intercept an owned DatabaseSync.exec around its real COMMIT may be reused to establish actual pre/post-COMMIT cut points without editing B12 source. Preserve the real transaction ordering. A fault injected after publishPrepared returns is after its reader ACK, and must not be named a pre-ACK fault.

5. **Timing follow-up: use a conservative public-call interval; exact production COMMIT instrumentation remains B12-owned if needed.**

The inspected store performs COMMIT in #transaction, then returns through unsafeRefs cleanup and the reader handoff's committed callback before publishPrepared returns. Consequently a timestamp immediately after the public call is a lower-bound start for commit-to-paint and omits real post-COMMIT ACK work. It cannot by itself qualify the specified commit-to-paint gate.

Do not replace the live handoff callback in production for telemetry. RecoveryIndexOverlay.snapshot defines that property as non-writable/non-configurable and freezes the handoff. Rebuilding the identity-backed handoff is unnecessary semantic risk and is outside this design choice. Callback entry would also remain later than COMMIT, optional, and absent on some paths; it is not a universal exact timestamp.

Within B10D, record monotonic entry and successful return around the existing per-instance publishPrepared public call, preserving this and its arguments/result. For a changed committed result, actual durable COMMIT return lies inside that interval. With paint enqueue P, call entry A, and successful return B, report [P-B, P-A] as the commit-to-paint interval, widened by documented clock uncertainty. The upper bound P-A includes all post-COMMIT work and can conservatively establish a pass when it meets the unchanged gate. A passing lower bound alone cannot. If the interval straddles a limit, mark exact qualification unresolved, not passed and not an established actual-gate failure. The selected-operation/full-operation series still includes every stage and failure independently.

Test-only exact COMMIT interception in isolated workers/processes can supply precise benchmark/failure-test timestamps, explicitly identified as instrumentation and included in the measured profile. Production exact telemetry or a narrower universally valid timestamp, if necessary, requires a B12-owned additive observability seam at the actual COMMIT-return boundary. That is separate from B12M's read-metering handoff. Do not silently redefine the contract around public method return.

For result paint timing, take the start marker before serialization/delivery work, and retain serialization, IPC, validation/decode, freshness, frame construction and enqueue in the trace. Keep per-operation samples; do not add stage percentiles or subtract the queue/main slice from progress.

7. **Follow-up: approve stable retained-order traversal for a disappearing eligible cursor.**

This is an in-scope correction to the existing fair scheduler in owned read-plan.ts and tick.ts. It implements the approved fairness rule without changing publication throughput, lease behavior, cadence, reader limits, deadlines or byte allowances. Proceed with the proposed minimal fix.

The inspected code locates afterKey in the filtered eligible array. Once a successful target stops being eligible, its index becomes -1 and selection restarts at the first eligible entry. tick.ts additionally supplies only eligible entries as schedulingTree.nodes, losing the retained position needed to avoid that restart. A stable prefix of follower targets can consequently be revisited after each later successful capture. This is a source-level fairness defect: with retained order [F0, F1, A, B], cursor A and current eligible set [F0, F1, B], the next target should be B, whereas the existing code chooses F0. With a larger follower prefix, repeated restarts multiply traversal work. The reported independent-process traces are consistent with this defect; they do not by themselves prove it is the only remaining cause of cold-start delay.

Use this precise rule:

- Construct the full bounded retained SessionRef order once per planning call, applying the existing scope, node-count and depth rules before testing eligibility. Use that same order to populate schedulingTree.nodes and to query pending(). Do not use all catalog/history entries or expand the retained scope.
- Keep continuation as the currently eligible subset, with its existing reason/identity checks. In planLinkRead, find afterKey in the full retained order, even when it is no longer eligible. Scan cyclically after that position and select the first eligible retained target; consider at most one full traversal. Membership lookup may be a temporary bounded map/set. Preserve the existing single eligible reason per target.
- If the cursor is absent from the full retained order, start at the first eligible target in that order. An initially absent cursor uses the same deterministic fallback. If no eligible target exists, return the existing no-target outcome. No cursor tombstones, global histories or additional scheduling queues are needed.
- Keep the retained order stable for a fixed scope/ready set; do not sort it by current eligibility, dirty status, lease ownership, recent success or process timing. Ordinary scope/topology membership changes still use the bounded current order and explicit absent-cursor fallback.
- Update the cursor only under the existing successful-plan rules. Deadline/byte failures must retain their existing cursor semantics, and the chosen target must still receive its required legal minimum or a visible deferred result. Do not use this fix to skip expensive readers repeatedly, grant several reads per operation, or claim an unperformed grant as progress.

Follower targets remain real eligible scheduling participants under the current collector policy. They may read compatible committed projections without opening a publication reader. Do not clear their dirty/caught-up state speculatively, suppress them by presumed ownership, or manufacture freshness merely to improve convergence. The fix is preserving the traversal position when another target leaves eligibility.

Add a deterministic regression that removes A from eligibility while retaining A in the full order and verifies B is next despite an eligible follower prefix. Also cover wraparound, a cursor removed from the retained scope, and a changing eligible subset over a fixed retained order: continuously eligible targets must not suffer a prefix restart each time a granted neighbor disappears. Exercise the tick wiring as well as the planner so an eligible-only schedulingTree.nodes cannot silently reintroduce the defect. Keep deadline/minimum-byte/one-grant behavior covered by the existing focused checks or the new regression where appropriate.

Then rerun the original independent simultaneous real-HUD cold-start case with its original bounds, dataset and independently progressing processes. Retain the prior failed runs and report per-session grants, oldest eligible age, continuation and drain time. A synchronized pair-step run may remain diagnostic evidence but cannot replace the independent case that exposed the problem. This approval predicts neither convergence time nor resource/performance acceptance; remaining failures retain the existing stopping/reporting rule.

This follow-up inspected source only, ran no probes, spawned no agents, and appended only this answer artifact. No new owner handoff is required for the traversal correction.

8. **Follow-up: desired relevance is not accepted relevance; pin owed publication.**

Approve the demand-token correction. The inspected observeLedger overwrites reading.demandToken on every observed ledger change, including for a resident reader. Admission can subsequently evict that accepted reader before the changed facts reach publishOne; with no later change, neither pending nor publication can recover the owed update. Observing a demand cannot acknowledge it.

Keep desired relevance and accepted relevance separate. observeLedger updates desired relevance and marks the appropriate demand; it never advances accepted relevance. Initialize accepted relevance as unknown, not as the current desired value (the empty token may itself be a valid value). Snapshot the relevance token together with the actual facts/context selected for publication. Advance accepted relevance only after that own publication succeeds for those facts, including a successfully evaluated durable no-op. An error, busy, follower projection read, preparation, observation of the ledger, or unrelated commit does not advance it. Never label old captured facts with a newer desired token.

An accepted resident reading whose desired token differs from its accepted token is not a quiescent eviction victim. Let the existing single-publication scheduler settle its owed facts using the retained prepared reading; this avoids needless native recapture. An already evicted reader retains explicit dirty demand until real recovery/recapture and publication settle it. The no-op publication memo must be invalidated by new owed demand. If conservative demand detection changes a token while the existing publication key is otherwise unchanged, either refine that detector to the existing semantic relevance or let the one selected publication evaluate a no-op; do not leave an unserviceable pin because due() ignores the owed token.

The same rule applies through run/source/binding changes and failures: the accepted token refers to a particular accepted context, and cannot survive an incompatible lineage as proof of acceptance. Existing invalidation/recovery semantics remain authoritative. No B12/B16 change or new publication opportunity is needed.

9. **Follow-up: bounded lifecycle retirement is permitted only with affirmative scope evidence.**

Same-root removal can end a session's collector lifecycle. This is distinct from evicting a still-in-scope cache entry to make space. An accepted partial tail may be dropped when that lifecycle genuinely ends: durable checkpoint/index state remains untouched, and any future re-entry uses the normal exact recovery path. This permission does not turn temporary display omission into lifecycle termination, nor authorize dropping an unresolved captured publication/outcome to satisfy resource targets.

Use one owned internal membership-reconciliation hook between LinkTickCollector's projection and SessionCollection, with three outcomes per retained reading: present, definitely absent, unknown. Derive it from the same authoritative ledger/topology inputs and root selection as B9, before rendered-node truncation and loaded-body filtering. It must not be a second edge resolver or status classifier. The existing projectLinkTree metadata reachability walk is a suitable place to expose a private membership certificate without changing renderer/public DTO semantics. Cache a certificate only while its root scope, ledger identity/boundary and relevant source-generation/topology tokens remain valid.

For a definitely-absent decision, require a current available ledger snapshot and complete, compatible structural evidence for the paths/cut needed to exclude the session from this root scope, including alternative native/delegated parents and the existing intent-root rules. A conservative certificate for the complete authoritative structural graph is acceptable. Individual proof of a disconnected cut is also acceptable when all alternative incoming paths are resolved by the same existing authorities. Native completeness means current matching generation/token, loaded topology, complete topology coverage, no omissions/gaps, and no conflicting identity/parent evidence. A removed body file or an absent UI node alone is not that proof.

Treat unloaded observations, node/depth/byte truncation, missing/dirty/stale topology, ledger unavailability, unresolved conflicts and missing frontier knowledge as unknown. Do not require every transcript body's coverage to be complete merely to prove a structural cut; a previously accepted incomplete body tail is exactly one of the states this lifecycle can retire. Conversely, a top-level tree coverage flag mixes structural and body reasons and cannot alone certify removal. Terminal run status by itself is not scope removal.

The minimal lifecycle is:

- A definite absence marks an existing record retiring and records its certificate/context. It stops receiving ordinary native reads/renewals merely because its body was formerly dirty. New facts do not create a separate retirement queue, timer or worker. If it becomes present again before finalization, cancel retirement and resume the same retained state; never create a second reader for that identity.
- A record with no captured pending candidate, no owed publication and no unresolved transport outcome can release its own valid lease best-effort and be removed. This includes an accepted partial-tail checkpoint. Lease/store work and cleanup time remain in the operation's accounting. If no authority is held, there is no invented release write.
- A record with a captured candidate or accepted reading owing publication remains pinned in the existing reader-slot limit. Retain only its node-scoped publication inputs/context and accepted baseline, not an entire old tree/view per retiring record. Let the ordinary publication scheduler select at most one target from active and retiring records together, fairly and with retirement/resource age visible. A selected attempted or no-op publication uses that operation's publication opportunity just as a changed commit does; counting only commit traces is insufficient to enforce this limit.
- For a retiring candidate, reuse its captured reading and normal B16 writer only with compatible current source/run/binding/ledger context. Last compatible facts may be retained, but known newer relevant facts must be resolved through the existing fact-building logic before claiming they were accepted. Do not publish an old run or old link state merely to free a slot. Existing explicit fencing/expiry/source/run/binding invalidation may reject/discard an unaccepted candidate without reader ACK, with a recorded superseded/fenced outcome and durable baseline preserved. This is the existing invalidation path, not a fabricated successful retirement publication.
- Busy or an unresolved compatible candidate remains pinned; a missing fact/context that cannot be safely established is visible retirement-blocked work. Do not reacquire fresh authority and use an old prepared candidate under it. If a correct settling path cannot be implemented through existing APIs, report that gap rather than guessing its baseline. Transport outcomes/accepted notices must be delivered or explicitly rejected/accounted for under the existing ACK protocol before their outcome state is removed. The worker's one-result backpressure still applies.
- After settlement and required result consumption, release the same publisher/lease best-effort, remove reading/reader/checkpoint/raw/envelope and prepared references, and remove its minimumBytes, pendingTopology, pendingCommits, demand, cached snapshot and stale scheduling references. Invalidate owned memo/index arrays that would otherwise retain the old envelopes. Do not delete durable observations, indexes or notice history. A later appearance is normal discovery/recovery, not revival of a retired callback.

Retirement state is bounded: retiring native state is part of the existing maximum 16 resident slots, never 16 extra readers; ordinary visible/active metadata remains bounded by the 200-node scope, and any retained retirement context must be compact and tied to those already retained slots. Do not accumulate an unbounded map of old nonresident sessions, certificates, publisher baselines or tombstones. Apply admission/backpressure before such retained metadata grows beyond the bounded implementation. Unknown membership is not an excuse to grow indefinitely: preserve the uncertain required state, defer new admission visibly and report the resulting resource qualification failure when the existing evidence cannot establish safe removal. Do not relabel uncertain nodes definitely absent to pass the limit.

Call reconciliation after a structurally current projection/certificate is available and before a later admission relies on the freed capacity. A topology update during the current read may establish retirement for that operation's normal publication/cleanup phase or the next ordinary opportunity; it does not justify a second read/publication. The hook and state machine are within collector/link ownership. No B12 contract change is needed for proven removal using existing valid release, commit, invalidation and recovery paths. Insufficient structural authority or an impossible settlement remains an explicit owner question, not permission for silent pruning.

Required regression evidence: a terminal/relevant fact arriving immediately before admission cannot be stranded by eviction; repeated observeLedger calls cannot clear its debt; same-root definite child removal releases accepted partial tails without native rereads; unknown/truncated topology does not; a retiring pending candidate uses the one publication opportunity and preserves accepted notices; busy/fenced/context-changed retirement is handled distinctly; reappearance before/after finalization is safe; repeated membership churn has bounded retained state. These exercise the existing correctness/resource obligations.

10. **Follow-up: native continuity must be recoverable as well as the checkpoint.**

The reported hidden-interruption case is a valid additional eviction guard: a working observation with an observed stateSince can have no recoverable codex-working-v1 anchor. Clearing the live NativeStatusMemory can then manufacture another observed interval after a zero-record recapture. Pin states whose accepted native continuity cannot be restored; an exact checkpoint identity alone is insufficient.

An acceptance-time detached trial using the existing restoreNativeStatusMemory and readerStatusSources functions is allowed within owned code. It must reproduce the actual compatibility checks used by prepare, operate only on detached trial memory/input, and never prepare/publish/ACK the hypothetical result or alter real read statistics. Cache the resulting eviction eligibility for that exact accepted reading/context and invalidate it on the next capture, commit, or context change. A trial resetContinuity=true conclusively disqualifies that eviction.
