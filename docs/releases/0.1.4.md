# 0.1.4

## A role is the work; where it runs is a list you switch

A role file now describes the work (`instructions`) apart from where it runs (`run`: an
ordered list of places across `pi`, `cli` and `bro`, the first is the primary, the rest
fallbacks). Old single-place role files still load as `run[0]`, and `"harness": "jev"`
loads as `"bro"`. `hud_create` runs on the role's first place that is installed and not
exhausted (`runs_on`); `on`, `model`, `thinking` and the pi switches still override one
job.

Shipped roles: `imp` and `reviewer` on pi, `sonic`, `architect`, `oracle`, `pro` and
`flow`. `oracle` is a local, read-only design advisor (`claude` `fable`, then the pi
architect); `pro` asks a strong web model (ChatGPT Pro, then Gemini, then AI Studio
Argon); `flow` makes images or videos (`kind`). The per-backend roles `grok-imp`,
`agy-imp`, `claude-imp`, `codex-imp`, `argon`, `gemini` and `flow-video` are gone. A role
runs on a CLI only with its instructions file (`implementer.md`, `reviewer.md`,
`oracle.md`).

When a job fails on a quota or rate limit, its place is marked exhausted for one hour
and the failure names the place the next dispatch will use; the HUD never retries a job
itself.

## The Control plane switches places

The Control plane page shows what needs you first: a role at its limit with the place
the next job will use, a role with nowhere to run, a role file that does not load. The
healthy roles and the files fold to one row each. On a role you change the harness,
model and thinking of a place, add, remove and reorder fallbacks, and clear an exhausted
mark; the change goes to `$HUD_HOME/roles/<role>.json` and the next dispatch uses it.
The model picker groups models by provider and shows the newest of each family; model
lists come from pi, agy and grok when the page opens (or on `r`), with the shipped
catalog as fallback.

## CLI workers end only on facts

A CLI worker's supervisor only observes. Only facts end a job: the worker's process gone,
its tab closed, or a dispatch rejected before input. A report settles the turn once it
has been stable for 10 seconds and the worker is not working; a background command the
worker started keeps the job open. A quiet turn without a report gets one Decision API
choice among fixed actions (keep waiting, one prompt to write the report, fail only with
a quota line on screen, or ask you); anything unclear goes to the main session. The
supervisor wakes on herdr events and file changes instead of polling, and writes STATUS
only when something changed. A dead supervisor with a live worker no longer fails the
job; `hud_send` to it starts a new one.

## The session hears what the panel shows

The panel, statusline, pi footer and MCP read jobs the same way. `hud_create` returns a
dispatch failure instead of a job id; every MCP response carries `changes`, the state
changes of the jobs this pane dispatched; `hud watch` prints them as they happen (Claude
Code runs it under Monitor). A working job's step-by-step flips are not changes. Nothing
is typed into the main session's pane.

## Project hub, second pass

The hub reads as a timeline: what waits for you, then Latest (folded first on a short
panel), then the pages. Progress shows the last seven days by date. Tickets are lanes:
For you, Working, Ready, Blocked, Done. Pages scroll; only the hub trims rows.
