## Findings

### 1. An incompatible old helper failure promotes a replacement primary to needs-you

**Severity: major** — `src/collectors/task-observations.ts:523`

`helperFailed` is assigned before the helper's producer timestamps are checked against the current primary, so an old STATUS in the reused pending slot can fail the new owner's card even though that helper is rejected as current activity.

Reproduced through `p2Fixture` → `PanelJobPipeline` → Work rendering: a replacement primary started one minute ago, with `helper_pending: {kind: 'review', n: 1}`, plus a leftover failed `review-1` that started an hour ago, produces `state: "needs-you"` and **“Work failed; inspect the job”**. The primary's observed state is still `waiting_helper`. The consult requires episode-compatible evidence and says failed helpers matter only while blocking the current owning phase; this old run cannot establish that failure.

**Suggested fix:** Validate current-primary/helper compatibility before admitting the helper's failure, signature, or other semantic facts. Add a real-file replacement-primary/reused-slot regression that checks the rendered state, not just the helper activity clock.

### 2. Production Work bypasses finished/native linger

**Severity: major** — `src/render/work-view.ts:70` (also summary at line 209 and `src/render/work-lanes.ts:39`)

The production sidecar path renders every `board.lanes` worker without applying the existing visibility/linger policy, so making `isExpired()` correct does not expire anything from Work.

Reproduced with a completed native worker whose `statusAt` is one hour old and `lingerMs: 60000`: `isExpired(...)` returns **true**, but the production frame still displays that worker and **“✓ 1 to accept”**. Closed facade workers likewise continue through the unconditional lane mapping. The new test at `tests/unit/work-card-p2.test.ts:367–369` checks `isExpired()` directly, but never checks that expired workers disappear from the rendered production viewport. This does not satisfy the explicit native-linger requirement or the implementation claim that linger remains as before.

**Suggested fix:** Apply the existing finished visibility policy to the production Work view, consistently across cards, summary, navigation and caches, while keeping successful facade-unclosed results pinned. Test actual rendered absence after linger, and continued presence before facade closure.

### 3. Readable current QA loses its question and default on both the card and Inspector

**Severity: major** — `src/render/work-card.ts:57–58`; `src/collectors/task-observations.ts:611–620`

The work projection retains only `requestId`, and `workCardDetail()` always replaces a readable request with “answer qN; inspect the job”; the available question/default never reach either display surface.

Reproduced with a current `qa/q2.md` containing a substantive question, explicit A/B options, and `Default if unanswered: A`: Work shows **“answer q2; inspect the job”**, and opening that direct task's Inspector repeats exactly the same instruction without the question or default. There is no answer decision yet, so the decision feed cannot recover the missing information either. The binding precedence table explicitly says to show the request/default when available; its generic fallback is for unavailable/current-question details, not every request. The current QA tests assert only the q-number and therefore miss this omission.

**Suggested fix:** Carry bounded parsed current-question/default facts and their evidence through the work model, reuse the existing question parser, and render them locally in the compact/expanded request detail and Inspector. Keep the generic fallback only when those facts are unavailable; this needs no model call or outbound grant.

### 4. Recorded browser phases are replaced by role-derived build/design phases

**Severity: major** — `src/collectors/workboard.ts:97–108`

The fallback `work.phases` is derived only from `job.role`, ignoring the recorded `job.runtimePhase` that is already assigned to `worker.phase`; the renderer consumes the former and therefore displays a false phase.

Reproduced with an oracle-through-Jev association and a running runtime record whose phase is `wait`: the collected worker has `phase: "wait"`, but its projected phases are **`["design"]`**, and both the lane and card display **“design”**. A Jev-executed association retaining the fixture's imp role instead gets “build”. Browser phase transitions can update activity correctly while remaining invisible or mislabelled in the actual cards. The consult requires recorded browser phases and actual role-corresponding phases, not a generic inferred workflow.

**Suggested fix:** Build phase facts from the compatible recorded executor/runtime/association evidence, with role-only fallback limited to cases the approved mapping actually supports. Extend the real-browser-fixture test to assert painted phase text and phase transitions, not just activity timestamps/state.

### 5. Facade/native-backed Inspector routing drops the new Work facts and phase history

**Severity: major** — `src/render/workboard-input.ts:42–43`; `src/render/work-view.ts:113–127`

Selecting a worker with `nodeId` clears `boardInspect` and routes to the old node Inspector, so the new Work detail section is used only for workers without a tree node; facade work's phase history, work state and activity basis never appear there.
