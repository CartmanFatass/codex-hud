## Findings

### 1. Major — a restored activation can permanently block a fresh installation

**`scripts/runtime-package/activation.mjs:344–345,453`** — The transaction/receipt name is derived only from target state, so returning targets to their original state reuses an existing receipt and makes a newly previewed activation impossible to apply.

**Failure scenario:** With an existing private HUD home, interrupt the first activation before its first managed mutation, then successfully run explicit restore. A fresh preview generates the same transaction ID; applying that fresh plan fails with `activation_already_attempted_restore_receipt`. Repeating restore does not help because receipts are intentionally retained. The same problem occurs without a fault: starting with an absent HUD home, two complete install/uninstall cycles succeed, but the third installation reuses the second receipt and fails. Both scenarios were reproduced with the real stage installer and activation code in temporary directories.

**Suggested fix:** Incorporate a checked, durable attempt/history head into the normalized preview and transaction ID, so a fresh preview after completed restoration has a new receipt identity while remaining deterministic and read-only. Preserve earlier receipts; add interrupted-restore/retry and repeated install/uninstall/reinstall coverage.

### 2. Major — interrupted restoration loses the proof required to reverse earlier activations

**`scripts/runtime-package/activation.mjs:550–556`** — A step whose restoration already happened is skipped on retry without recording `phase: restored` and `restoredState`, preventing earlier receipts from recognizing the legitimate replacement inode.

**Failure scenario:** Activate N, upgrade to N+1, and interrupt restoration of N+1 after the real atomic rename restoring N's `current` but before the journal completion write. Retrying restoration reports `deactivated; release retained`, yet the selector entry remains `phase: after`, `restoreIntent: true`, with no `restoredState`. Restoring N's original receipt then returns `CONFLICT` for `current`, despite the correct original bytes/mode being present. `recordedRestoration()` cannot establish the restoration because it requires the missing completed journal entry. Reproduced by injecting an error immediately after the actual selector rename; an open descriptor kept the original inode from being reused.

**Suggested fix:** Represent these already-restored steps as reconciliation actions and, under the restore locks, durably finalize their restored state before reporting success. Add failure-window coverage between each reverse mutation and its completion record, including upgrade rollback followed by reversal of the older activation.

### 3. Minor — the bundle bootstrap exits successfully when restoration/uninstall conflicts

**`scripts/activate-runtime.mjs:6–9`** — The bootstrap prints a `CONFLICT` result but leaves exit status zero, unlike the installed CLI's exit status 4 for the same refusal.

**Failure scenario:** Hand-edit an installed public shim, preview uninstall, and apply that exact uninstall plan through `node BUNDLE/activate-runtime.mjs`. The command exits **0** with JSON `status: "CONFLICT"`, although nothing was deactivated; shell automation using `&&` or exit status treats the refusal as success. The same temporary fixture through `bin/hud` exits **4**. Both paths were exercised.

**Suggested fix:** Propagate a nonzero conflict exit code from the bootstrap, matching `src/cli/install.ts`, and add a bootstrap conflict/exit-code regression test.
