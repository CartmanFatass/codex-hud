## Findings

### 1. Major — QA pair validation cannot finish when a source exceeds one metadata slice

**`src/collectors/task-observations.ts:331–355`** — `project()` revalidates every cached question/answer pair in one pass, and exhaustion of the shared 64-probe allowance sets `qaPending` and `dirty` again without retaining per-pair validation progress.

**Failure scenario:** Create one safe task directory with 50 valid, unchanged QA pairs—within the plan's 100-pair bound. After 300 refreshes, the production `PanelJobPipeline` contains all 50 calls, but **23 remain individually stale**. Over another 100 unchanged refreshes, **zero snapshots become complete and zero slices have zero reparses**. Each slice uses 64 probes, zero body reads, zero enumerations and one reprojection, retaining `qa_pair_pending`, `observation_pending` and `source_unavailable`. The standalone collector produces the same result. This is not an initial catch-up or an unreadable source: the new all-pairs validation pass requires more probes than any slice permits and continually restarts. It violates plan §3's fair incremental catch-up and unchanged-warm zero-reparse requirements, while incorrectly presenting readable, unchanged evidence as stale.

The new R3 regression test exercises only one pair, so it verifies mixed-revision safety but misses this failure.

**Suggested fix:** Retain coherent reductions and pending dependency validation per pair, keyed by the pair's signatures, with a persistent bounded cursor. Do not invalidate/reparse every already-coherent pair merely because another pair was deferred. Add a real-disk 50–100-pair pipeline regression that eventually reaches complete/fresh coverage and zero warm reparses, preserving the one-file mixed-revision test.
