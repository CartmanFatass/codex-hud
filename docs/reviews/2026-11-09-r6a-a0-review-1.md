## Findings

### 1. Import can override existing AI Studio configuration through its supported legacy aliases

- **Severity:** major
- **Location:** `src/cli/import.ts:67`, `src/cli/import.ts:240–247`
- **Defect:** The existing-wins merge compares literal JSON keys, but the importer writes camelCase AI Studio keys whose runtime precedence overrides existing snake_case HUD values.
- **Failure scenario:** An existing HUD `config.json` contains `aistudio.state_dir`, `default_model`, `default_thinking` and `cdp_url`, which `loadStudioConfig` explicitly still supports. Importing a TOML with different values adds `stateDir`, `model`, `thinking` and `cdpUrl` instead of reporting conflicts. I reproduced preview reporting `add 4`, apply returning 0, and the effective configuration changing from the existing state directory/model/Low/9333 to the imported directory/model/High/9444. Switching the shared state directory can also bypass the operation records that protect prior sends. This violates the binding existing-HUD-value-wins requirement even though the old JSON properties remain present.
- **Suggested fix:** Treat supported aliases as the same logical destination key when detecting conflicts; preserve the existing effective value and report the skip. Add an import test starting with the previously supported snake_case HUD configuration and compare runtime-resolved values before and after apply.

### 2. A one-call fallback becomes the job's primary provider on resume

- **Severity:** major
- **Location:** `src/jev/runtime/executor.ts:961` and `src/jev/runtime/executor.ts:519–521`
- **Defect:** Recording the actual responder overwrites `job.provider`, while resume still interprets that field as the original provider binding.
- **Failure scenario:** With primary TypeSafe and fallback OpenAI, one TypeSafe quota failure causes an OpenAI answer and persists `provider.id = openai`. After interruption, `readJob(..., { resume: true })` passes that responder as an explicit primary to `resolveDecision`; the configured OpenAI fallback then equals the new primary and is removed. A recovered TypeSafe provider is never tried, and a subsequent OpenAI failure cannot use the intended provider policy. An isolated synthetic restart receipt with a recorded TypeSafe→OpenAI quota fallback reproduced `PROVIDERS CONSTRUCTED FOR RESUME [ { id: 'openai', fallback: undefined } ]`, despite configuration remaining `{ primary: 'typesafe', fallback: 'openai' }` and both keys being present.
- **Suggested fix:** Persist the job's original decision binding separately from actual-response metadata, and resolve resumes from that binding rather than the last responder. Add a restart-after-real-fallback test proving the next decision starts with the original primary and never repeats Send.

### 3. Import can successfully publish credentials that its own reader refuses

- **Severity:** major
- **Location:** `src/cli/import.ts:70–71`, `src/cli/import.ts:122`
- **Defect:** Input files are bounded, but the fully merged/serialized destination is not checked against its reader's size limit before publication.
- **Failure scenario:** I imported a 40,014-byte `.env` source into a valid 40,044-byte `credentials.env`, using distinct `TEXT_MODEL_*` names and a synthetic Mistral key. Apply returned 0 and replaced the destination with 80,060 bytes. `readHudCredentials` then failed `jev_env_perms: ... maximum 64 KiB`, disabling even the previously valid key, and the second identical apply returned 1 instead of being an idempotent no-op. Multiple individually bounded sources can produce the same problem; JSON serialization can also exceed the settings/import limit.
- **Suggested fix:** Validate every final staged destination against its applicable size limit during planning, before creating directories, backups or replacing any destination. Cover oversized aggregate merges and JSON expansion, asserting refusal leaves the destination tree unchanged.
