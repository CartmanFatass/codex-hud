2. Required amendments to recovery and execution — §§5.1–5.3, §10
A. Distinguish an unstarted instance from an uncertain dispatch

The recovery table currently sends an agent with no verdict and no nativeRef to on.lost. That covers neither side of the dispatch boundary correctly:

An instance may still be waiting and have never been dispatched.
A launch or input submission may have happened before its returned reference was recorded.

Specify this invariant:

Before every launch or input submission, persist a unique dispatch/attempt identity and its intent. Associate returned child, turn, process or Jev references with that identity. An instance with no dispatch intent is unstarted and returns to admission. An intent without a conclusive result must be reconciled against recorded launch/session/process evidence; absence of a nativeRef does not prove that dispatch did not occur.

If an attempted agent dispatch cannot be reconciled and has no recoverable native session, stop at needs_owner{uncertain_work}. Do not automatically follow an edge that can repeat the work.

For commands, this also resolves the schema’s present impossibility: a PGID cannot be recorded before the process exists. The intent precedes spawning; the PGID and process-start marker follow it.

When settling an instance, persist its result, selected edge, counter changes and successor instance identity—or an explicit pending-successor cursor—in one run-record rewrite. That makes the already-listed “after settlement before successor” crash test implementable without guessing which transition occurred. 
WF1 §5.1–§5.3

B. A verdict file is not evidence that a turn completed

Replace the first recovery-table row. A valid verdict.json proves that the child wrote a file. It does not prove that the corresponding turn completed successfully.

The rule should be:

Recover an agent outcome only from terminal evidence matching the instance’s current dispatch and turn. A matching successful completion enters the same verdict-validation/question transition used during live execution. Matching failed or interrupted completion retains the ordinary failure, timeout and cancellation precedence. A verdict file without matching completion evidence remains uncertain evidence.

The native design already persists ChildRecord.outcome.turn and terminal outcome information. Extend the normalized event contract to carry the originating turn/attempt identity needed by WF1’s late-event check. Do not identify an old event by reading the child’s current turn when the event is processed. 
WF1 §3, §5.3; 
native HUD §2.8

C. Command completion needs a structured host receipt

Replace “exit line in output.txt → settle” with:

Recover command completion from a host-authored receipt containing its attempt identity, exit code or termination cause, and completion time. The receipt may live in an existing durable host record. output.txt is the bounded display log and is not completion authority.

A command can itself print text resembling an exit footer. Without a matching receipt, use the existing uncertain-command rule: replay only when declared idempotent or explicitly authorized.

D. Persist group stop and apply recovery precedence consistently

Add a durable group-stop field, for example:

TypeScript
groupStop?: {
  cause: 'member_failed';
  member: string;
  at: number;
};

Persist it before cancelling siblings. join.decided is the final aggregate decision; it does not represent the intermediate state in which a group has failed but sibling cleanup remains unfinished.

Prepend these rules to §5.3:

Persisted run stop and timeout causes retain precedence during recovery. A stopped run performs cleanup only and follows no successor edge. A stopped group settles its remaining members before settling the container. New dispatches, replays and continuations must pass the original absolute deadlines and remaining budget. Recovery never resets deadlines, edge counters, question counts or nudgeUsed.

Use matching terminal receipt timestamps to preserve work already completed before a deadline. An elapsed deadline prevents new execution; it should not manufacture a timeout for an already-recorded timely completion. 
WF1 §2.1, §5.1–§5.3

E. Make the advertised command replay reachable

Keep the explicit replay feature. Amend §10 so that workflow_start also accepts a run in needs_owner{uncertain_command}, subject to all of these conditions:

replay names exactly the unresolved uncertain command instances being authorized.
Settled, unknown or unrelated instance IDs are rejected.
Replay creates a new attempt under the same logical instance, preserving prior artifacts.
The original run/step deadlines, counters, budget and frozen bundle remain in force.
Other terminal outcomes do not become generally restartable.

This closes the contradiction between §5.3’s promised replay call and §10’s restriction to proposed/`interrupted`.

Also standardize the admission error: failed{capacity} for admission timeout; failed{dispatch} for a create/spawn failure. Both route through on.failed. 
WF1 §5.2–§5.3, §10

3. Required composition and reuse amendments — §§2–2.1, §3
A. Validate routing against the step’s routed outcomes

Replace the universal “every verdict needs an edge / edge token must be in verdicts” statements with the following typed contract:

Construct	Required routing
Sequential agent	Every declared verdict token; default done
Sequential command	pass, fail
Parallel container	accept, reject
Foreach container	accept, reject, empty
Parallel leaf	No on.*; its result returns to the container
Foreach member	verdicts describes each item’s agent outcomes; the enclosing step’s on.* routes the container outcome
Jev, once enabled	answered, incomplete; handoffs are handled outside graph routing

For routable steps, failed, timeout and lost are host-generated outcomes with optional handlers and the documented defaults. They are not rejected merely because they are absent from an agent’s verdicts.

question is intercepted by the verdict protocol and is never a graph edge.

This is a genuine revision-2 inconsistency: a parallel leaf currently must both have and not have on.*; a foreach step similarly mixes its member and container outcome alphabets. 
WF1 §2–§2.1

B. Bind reuse to an existing, deterministic instance

Add:

A reuse target must be a distinct sequential agent step that strictly dominates the reusing step. At dispatch, bind to the latest settled instance of that target preceding the current instance, and persist its instance ID and child reference. The existing identical-bundled-agent rule remains mandatory.

If that target instance has no usable child/native session, produce failed{reuse_unavailable} through on.failed. Do not silently choose an older instance or create a fresh child.

This rejects self/mutual reuse and branch paths that reach a reuse step before its target has executed. It also gives repeated target steps a definite meaning. Keep revision 2’s decision that cache warmth never changes this selection. 
WF1 §2 reuse rule; §8.3

C. Admit the example’s typed argv shorthand explicitly

However, run = "{check}" is a string in TOML, while §3 currently permits only an argv array. Add:

run = "{<argv-param>}" is permitted only when the entire value references a declared kind = "argv" parameter. Resolution replaces it with that argv array before plan display and bundling. Other string-valued run forms are invalid; shell execution uses the explicit shell form.

W1 must assert that the example normalizes to ["npm", "test"].

Also change W1’s round-trip wording to: “Normalization is preserved across TOML/JSON round-trip; repeated canonical TOML serialization is byte-stable.” Ordinary normalized JSON does not preserve arbitrary original TOML comments and formatting. 
WF1 §2 example, §3, §12 W1

4. Required verdict and question amendments — §§3, 6
A. Make verdict artifacts dispatch-specific

An initially empty instance directory prevents stale artifacts from a previous instance. It does not prevent stale artifacts across a nudge, answer continuation or recovery continuation within the same instance.

Use a fresh verdict destination for each issued prompt, such as:

纯文本
<instance>/attempt-<n>/verdict.json

Persist the dispatch identity and path before issuing that prompt, and name that exact path in the trailer. Consume only that dispatch’s artifact, together with its matching successful turn completion.

{verdict:<s>} should resolve to the accepted terminal artifact of the bound instance. Keep nudgeUsed, question count, budget and deadline at instance scope, so changing attempt directories cannot reset them. 
WF1 §3

B. Make question consumption and answering durable

Specify this order:

Validate the question verdict.
Persist the question payload, stable request ID, incremented question count and asking state.
Archive the file idempotently.
Publish/project the request.

The persisted request is authoritative. A crash between recording and archiving must not create another question or lose the existing one.

On hud_respond, persist the accepted answer and continuation intent in the run’s serialized transition before sending. Recovery reconciles that intent under the dispatch rules above. A duplicate response remains request_not_pending; an answer after stop records no new execution.

This preserves the intended single continuation without assuming that moving a file and rewriting a record are one atomic operation.

C. Define the question variant completely

For verdict: "question", require a nonempty bounded question.text. Validate option strings and the default; when options are supplied, the default must identify one of them. A missing or malformed question payload is bad_verdict and uses the existing single persisted repair allowance.

D. Strengthen Pi default correlation

Keep the P7 gate, but make its success criterion stronger than “tool arguments are visible”:

Prefer the harness’s tool-call/request identifier. Otherwise match only within the same active turn against exactly one unmatched, causally preceding ask_orchestrator call with the same title/options. Consume that match once. Missing or ambiguous correlation is other and wakes the owner.

Add repeated identical questions with different defaults and multiple outstanding calls to P7. Until that linkage is demonstrated, the existing fallback to wake remains correct. 
WF1 §6

5. Required cache amendment — §8

The revised normalization and advisory-only reuse policy should stand. The remaining defect is timestamp semantics.

§8 permits turn completion to seed lastRequestAt, but C1 requires that a four-minute response not refresh the cache timer at completion. Those rules conflict. Moreover, turn_started does not necessarily identify the last model request in a turn containing tool loops. 
WF1 §8.1–§8.2; §12 C1

Use this rule:

request_start requires an observed model-request start. A turn start may be used as a conservative turn_start_estimate; it must not be labelled an observed request start. If neither is available, forecast timing and expiry remain unknown. Turn completion never starts or refreshes the cache timer.

Accordingly, change the timestamp discriminator to:

TypeScript
lastRequestAtIs:
  | 'request_start'
  | 'turn_start_estimate'
  | null;

After compaction or resume, invalidate the prior forecast anchor until new evidence after that boundary is observed. Historical usage can remain visible without restoring the old forecast.

Keep the conservative openai: null default. Delete the unverified “30-minute minimum / 12-hour option” aside: it contributes nothing to the chosen Codex subscription policy. Retain the separation between observed token usage, TTL assumptions, and conversation reuse.

7. Jev: approve both requested additions, with the following contract
A. Correct the workflow state mapping

The companion’s state machine explicitly includes queued and sending, and treats interrupted as recoverable bookkeeping. Its wake policy also escalates uncertainty remaining after reconciliation. WF1 must preserve those meanings when it consumes Jev’s wakes. 
JEV1 §§4.7–4.8

Use this mapping:

Jev condition	Workflow behavior
queued, sending, sent, awaiting, reconciling	Active, unsettled work
Initial uncertain while the permitted automatic reconciliation is pending	Active, unsettled work
uncertain remaining after that reconciliation	Block with an external-operation intervention and emit one run-level intervention notice
needs_human	Block with an external handoff; never answer through hud_respond
interrupted	Recover from the authoritative operation record; do not immediately settle failed
answered, incomplete	Route the corresponding result token
Other stated failure outcomes	Retain the documented failure routing and reason
dry_run_ok	Unreachable for an enabled workflow Jev step

For recovery, distinguish these cases explicitly:

Sent operation: resume waiting.
Attempted send with uncertain effect: use JEV1’s permitted read-only reconciliation.
Record proving no send was attempted: the original first send may be started using the same frozen operation identity and ordinary deadline/admission checks.
Released key: generic workflow recovery never manufactures confirm_resend:true.

The last two cases are different. JEV1 says resume does not start a send, so “all recovery uses wait/reconcile” is insufficient for an interruption before the first send. 
JEV1 §§4.4–4.7

Snapshot the resolved prompt bytes and digest before the instance’s first submission, then preserve them across recovery. Generate a bounded deterministic slug from owner/run/instance identity rather than truncating an arbitrarily long concatenation. Persist the resulting label and key before submission.

B. Make handoffs operationally resumable

Amend §6’s precedence:

Approvals, unknown dialogs and Jev external handoffs always require intervention. wake/default/fail applies only to answerable questions.

Change the request origin from mandatory child: string to a discriminated origin, for example:

TypeScript
source:
  | { kind: 'child'; child: string }
  | { kind: 'jev'; key: string };

Record the request on its originating work record and the workflow run.

Also extend workflow_start{run} to accept a workflow blocked on a Jev external intervention, after the owner has addressed it. It then performs the record-based recovery described above, retaining the same instance, key, deadlines and budget. It cannot supply resend confirmation.

This closes the current passive statement that the run resumes “when the job leaves needs_human”: JEV1 permits that state to have no active observation task, so the document must name the action that restarts permitted observation or first-send work. 
WF1 §§5.4, 6, 10; 
JEV1 §4.7

C. Approve jev_ask workflow ownership metadata

Approve owned_by: 'workflow:<run>'. Define it as routing and lifecycle metadata, while retaining the existing authenticated HUD owner.

The contract must require:

The referenced run belongs to the authenticated owner.
The run/instance association is persisted before execution or event production.
A repeated ask with the same key and association returns the existing job.
A conflicting association is rejected; it cannot silently take over another job’s wakes.
The association survives restart.
Raw job events remain readable, while wake decisions enter the run’s serialized transition queue.
Completion and intervention notifications are emitted at run level, including persistent uncertainty.
Jobs without workflow ownership retain ordinary Jev wake behavior.

The metadata must not change JEV1’s provider/label/prompt operation-key calculation. 
WF1 §5.4; 
JEV1 §§4.5, 4.7–4.8

D. Approve idempotent terminal jev_ask_close

Approve it for terminal and already-closed known jobs.

Specify:

Repeated close returns success with the current {ok, run, work} result. It preserves the authoritative operation outcome, answer files and send/release evidence. It completes or joins any remaining observation cleanup, using the original close deadline and existing sent-tab rules.

A terminal job can still have an observer handle awaiting cleanup. Concurrent closes should join the same cleanup operation rather than restart its timeout. Closing after answered must not rewrite the Jev outcome as cancelled or emit another completion wake. Unknown keys can retain a typed not-found result.

This makes answer-versus-cancel races straightforward: the workflow’s cancellation outcome and the Jev operation’s recorded answer remain separate facts. 
JEV1 §§4.4, 4.7
