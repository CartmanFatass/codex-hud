## Findings

### 1. Blocker — `.dispatch/current.json` makes `sessionFolders` throw ENOTDIR, so the watcher dies on the first scan of any job that used a helper dispatch

**Where:** `packages/hud-mcp/bin/hud-watch.mjs:105-109` (the `.dispatch` mapping at `:108` and the `lstatSync`
filter at `:109`), called from `:152` in every scan before the job's status is read.

**What the owner sees:** the watcher exits 1 on its first scan; finished jobs' herdr tabs stay open and
JOB-RETENTION never deletes anything. `ensureWatcher` (`packages/hud-mcp/src/thin-main.ts:195-209`) restarts it on
the next `hud_*` call and it dies again. This is the round-4 symptom, now on the normal job layout rather than a
rare link loop.

**Why:** pi-roles writes `<job>/.dispatch/current.json` as a regular file for every helper dispatch
(`<pi-roles>/bin/pi-role-call:175`, via `atomicJson`; the HUD's own status reader filters `.dispatch`
entries with `entry.isDirectory()` for exactly this reason, `src/roles/pi-dispatch-status.ts:319-327`).
`sessionFolders` maps every `.dispatch` entry to `<entry>/sessions` and filters with
`fs.lstatSync(folder, { throwIfNoEntry: false })`. That option suppresses only ENOENT; `current.json/sessions` is
ENOTDIR, which throws out of `scan()`. The old code used `fs.existsSync(folder)` inside `preserveSessions` (returns
false on ENOTDIR) and only touched `.dispatch` for expired jobs; the new function is called for every job, outside
any catch.

**Evidence:**
- Real tree (read-only, no writes, no watcher run against it): 74 job dirs, 4 with `.dispatch/current.json` —
  `j22917b414696dc24` (M4-PRUNE2), `jb2ac49661846dc67` (M3b), `jcb90694225c833f3` (M3b), `jfa674fa0724f7af1`
  (M3b); all normal implementer jobs with sonic helpers.
- Probe with the exact layout (`sessions/`, `.dispatch/current.json`, `.dispatch/helper/sessions/`) and an open
  job: the reviewed watcher exits 1 with `Error: ENOTDIR: not a directory, lstat
  '<job>/.dispatch/current.json/sessions'` at `hud-watch.mjs:109`. The same probe with only an expired closed job
  exits 1 and leaves the job and its session file in place (instead of deleting them).
- The `6a27a421` watcher, run from `git show` through `tmp/env.sh` on the same layout, stays alive and exits 0 when
  the job closes.
- `fs.existsSync('<file>/sessions')` is `false`; `fs.lstatSync('<file>/sessions', { throwIfNoEntry: false })`
  throws ENOTDIR.
- No test creates `.dispatch/current.json`: the 26 green tests only use `.dispatch/helper/sessions`, which is why
  the suite stays green.

**Smallest fix:** filter `.dispatch` entries to directories before joining, e.g.
`fs.readdirSync(dispatch, { withFileTypes: true }).filter((entry) => entry.isDirectory()).map((entry) =>
join(dispatch, entry.name, 'sessions'))` (and, if wanted, wrap the `.dispatch` read in a try/catch for a
`.dispatch` that is itself a file). Add one regression test with `.dispatch/current.json` plus
`.dispatch/helper/sessions`, for an open and an expired job.

  the watcher sleeps until the deadline with no watch and no poll; a job created in that window is not seen until
  the deadline (up to 2 h). Probe: permanent `fs.watch` failure + a failed tabbed job + a new open job → 1 scan,
  the new job never scanned, the watcher alive. Requires a permanently failing watch; the stated design polls only
  while jobs are open. Fix if wanted: also poll when `!watcher` (not only when `open`), or retry the watch on the
  timer.
- `packages/hud-mcp/bin/hud-watch.mjs:236` — a later watcher error never retries the watch; the process polls at
  1 Hz for as long as jobs are open. This matches the stated degraded-mode design, but a transient error
  permanently degrades until the process exits. Fix if wanted: retry `startWatch()` after the next scan, as at
  startup.
