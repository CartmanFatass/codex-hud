## Findings

### 1. Budget-wide metadata memoization lets a revoked request pass the send fence

**`src/core/materials/job.ts:210`**, together with **`src/collectors/small-model.ts:1116`** — Cached path metadata is reused across authorization, composition, lifecycle callbacks and dispatch, so a durable revocation within that synchronous scope is invisible to subsequent authorization checks. **Severity: major.**

Concrete scenario: submit an authorized job through the real `SmallModel`, and have its supported synchronous `onChange` callback call `authority.setConsent(recipientId, 'deny', ...)` when the request is queued. The policy is atomically replaced and `refresh()` notifies subscribers, but the active budget still holds the old policy stat. `policy()` consequently reuses the old cached policy; both the revocation listener and the final dispatch checks consider the request authorized. One transport call sends the job material after revocation. The eventual reply is denied only after the synchronous budget scope has ended, which cannot undo the outbound disclosure.

An independent synthetic production-path probe returned:

```text
lifecycle policy on disk: deny
transport calls after onChange revocation: 1
settlement: {"ok":false,"error":"requires_authorization","refused":true,"cancelled":true}
```

A separate probe revoking consent inside `compose` produced the same one-call leak. Existing revocation tests revoke only after `submit` returns, when a new metadata scope is used, so they miss this regression.

**Suggested fix:** Do not reuse an earlier metadata snapshot as a later security fence. Invalidate policy/path memoization on consent changes and ensure post-callback/send validation obtains fresh security-critical identity/policy evidence, with all probes still budgeted. Add synchronous lifecycle- and compose-time revocation regressions asserting **zero transport calls**.

### 2. Late budget exhaustion is still converted into an authorization refusal

**`src/collectors/small-model.ts:1298–1301`** — The post-compose validation throws `JobBudgetPending` when the caller's deadline expires, but the generic catch erases that distinction and returns `requires_authorization` instead of the job-specific pending outcome. **Severity: major.**

Concrete scenario: an authorized job completes material extraction, then prompt composition crosses the supplied soft deadline. No grant or source changed. Revalidation throws on the expired deadline, and the handle settles as refused rather than telling P3b to retry with a fresh budget. This leaves the earlier budget-deferral repair incomplete at the actual SmallModel boundary.

An independent probe used the real authority, adapter and SmallModel, with an initially future deadline and composition running until that deadline naturally elapsed:

```text
natural deadline crossing result: {"ok":false,"error":"requires_authorization","refused":true}
transport calls before retry: 0
fresh-budget retry: {"ok":true,"text":"Synthetic sentence."}
transport calls after retry: 1
```

The review-time **q7** ruling explicitly confirms this is a required P3a fix. Late pending may already have performed compose work; the zero-work guarantee applies to preflight pending. Late pending must discard the composed request and do no transport, cache write, failure telemetry or hourly-cap charge. A real revocation/source change still takes precedence as a deny.

**Suggested fix:** Preserve `JobBudgetPending` through the job-only submit boundary before the generic authorization catch, returning `{ok:false,pending:true,reason:'budget'}` without queue/cache/cap side effects. Add q7's late-expiry, revoke-plus-expiry and fresh-budget retry regressions; do not widen shared native result/status types.
