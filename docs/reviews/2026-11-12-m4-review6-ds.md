## Findings

### 1. Major — an open job whose scan throws is counted as "nothing open", so the watcher exits while the job is still open

**Where:** `packages/hud-mcp/bin/hud-watch.mjs:147-214` (the per-job try/catch) and `:224` (`else if (!open) stop()`).
The session work that can throw (`sessionFolders` at `:149`, the loop cleanup at `:149-156`) runs before the STATUS
read at `:160` and before `open` is set at `:170`, `:174` and `:178`. The catch at `:212-214` logs and skips the job
without recording that its state is unknown.

**What the owner sees:** a job directory with one odd entry (an unreadable `sessions/`, or `.dispatch` as a regular
file) makes the scan throw for that job. If it is the only job, the same scan reaches `:224` with `open === false`
and `nearest === Infinity`, so the watcher removes `watch.pid` and exits 0 while the job is open. `ensureWatcher`
(`packages/hud-mcp/src/thin-main.ts:195-209`) starts a new one on the next `hud_*` call and it exits again: the open
job's tab is never closed and JOB-RETENTION never runs — the round-4/5 symptom, now silent instead of a crash.

**Evidence (real watcher, temporary homes through `tmp/env.sh`):**
- one `working` job, `sessions/` chmod 000, no other job: `keep j0000000000000001 scan: EACCES ... scandir
  '<job>/sessions'` then `exit pid=...: no open jobs or failed deadlines`, exit 0, job still `working`, its tab
  never reaped;
- one `working` tabbed job, `.dispatch` written as a regular file, no other job: `keep ... scan: ENOTDIR ... scandir
  '<job>/.dispatch'` then exit 0 in the first scan, tab untouched;
- the new odd-entry test (`tests/unit/job-retention.test.mjs:96-129`) only uses an `expired()` bad job, so it asserts
  the opposite case (a *terminal* bad job is retained and the watcher exits) and never covers an open one.

**Reachability:** the owner's tree has none of these shapes today (77 job dirs, 4 with `.dispatch/current.json`, no
`.dispatch` file, no unreadable directory, no symlinked or looped session folder), so this is not normal use; it is
the containment half of the DS round-5 optional notes, which M4-FIX5 was asked to close. The design intent's "one
job's error is logged and skipped" can be read as accepting it — but then the brief's check "an open job whose scan
fails is not mistaken for 'nothing open'" is unmet, and the failure is the watcher-lifecycle one that has bitten
this feature twice.

**Smallest fix:** determine `open` before the session work — read `job.json`/`STATUS.json`/`SESSION.txt` first, set
`open` for the open states, and run the loop cleanup in its own try so an open job's cleanup failure cannot clear
the flag. A one-line alternative (`open = true` in the catch) also keeps the watcher alive, but it makes a
permanently bad *terminal* job keep the process alive forever and would require changing the exit expectation of
`an odd dispatch file does not block deletion and reaping of other jobs`.

## Optional (does not change the verdict)

- `packages/hud-mcp/bin/hud-watch.mjs:218-221,239-241` — a *persistent asynchronous* `fs.watch` error turns the
  retry into a tight loop: each scan installs a watcher whose `error` handler immediately schedules another scan.
  Probe with a synthetic watcher that emits `error` on the next tick every time: **11,225 scans and 11,243 log lines
  in 1.5 s** (≈7.5 k/s, `watch.log` ≈1 MB/s). I could not produce a repeated async error with the real recursive
  watcher (an unreadable subdirectory throws synchronously and settles at 1 scan/s; 200 create+delete subdirectories
  produced no error), so this needs a coincidence. Fix if wanted: only retry on the 1 s timer, or ignore an `error`
  that arrives before the next scan.
- `packages/hud-mcp/bin/hud-watch.mjs:213,222,242` — in degraded mode the retry logs one `watch error` line per
  second (and one `keep <id> scan` line per bad job per scan) for as long as the watcher lives; `watch.log` is
  trimmed to 200 lines only at startup, so a permanently broken `fs.watch` grows it ~8 MB/day. Bounded per scan, not
  over a long run. Fix if wanted: log the retry at most once a minute.
