Spec — blocking

1. Split Project's second click is not Enter. src/render/split-input.ts:77–90 calls Classic activation directly on a second click on the selected list row, bypassing Split's `intoPreview`. On the hub's Waiting row, keyboard Enter focuses the waiting items while a second click toggles a Classic fold that Split does not use. On a Control plane role, Enter focuses the places while a second click does nothing. Use one Split Enter path for the key and the second click, with the current Classic fallback for opening pages and files.

2. Split has no way to read the brief for an older-milestone slice that is still to try. src/render/split-project.ts:54–65 renders hub to-try rows without briefs; :77–102 selects and explains slices from `currentRows(data)` only. For example, the shipped synthetic hub shows WATCH-LINK (M4) while the current milestone is 0.1.3. It is among the newest 12 and can get a brief, but it has no selectable slice preview in Split Progress, and selecting its hub row does not show the brief. The owner can accept it from Split but cannot read the acceptance steps in that layout. Keep the milestone bar if desired, but give those slices a route to their brief without switching layouts.

3. Classic can still cut the selected waiting item to one line. src/render/project-view.ts:258–264, :288–296 enables whole text for the selected item only if some hub tier fits with one line per item. At 40×24, enough waiting items and Now rows to exceed 22 body rows after dropping Latest, bar and gaps hit the final `build(0, false, false)`. It drops the selected item's continuation even though the hub already scrolls. Keep the selected item whole in that fallback as well. The separate Waiting page is not a substitute for 04's selected-row rule.

4. Try-brief generation starts while the Projects list is open. src/tree-page.ts:990–1010 uses `projectShown` for both the list and the selected project. `collect(false)` correctly pauses full collection in the list, but `tryBriefs.update` still takes the prior snapshot and can start requests from it. Open the list after viewing a project with more than three eligible slices, or leave it open through a ticket recheck: the previous project's inputs can still go out while only the overview list is on screen. Gate starting briefs on the actual selected-project view, not the Project tab alone.

Simplicity and quality — blocking

1. Split can record a decision for a slice that is not on screen. src/render/split-input.ts:91–101 searches all preview rows for the first pending target; src/render/split-frame.ts:64–71, :84–87 reveals only an explicit preview cursor and draws the implicit band only if it happens to be visible. On the fixture's 40×24 Split hub, PgDn scrolls past DATA-ONE while leaving focus on the Progress list row; `y` or `n` still writes DATA-ONE, not a slice in the visible part of the preview. At 40×12 the first pending row can be hidden even on entry. Keep the agreed first-pending shortcut, but reveal or explicitly identify the actual target before writing when it is off-screen; don't write a blind decision.

2. Marking a slice breaks automatic panel reload. src/render/monitor.ts:63–64 adds a `Map` to monitor state; src/utils/panel-reload.ts:8–16, :51–54 only encodes/revives Sets, so a nonempty selection returns as `{}` via src/tree-page.ts:524. With a to-try view open and a mark pending, the next build reloads into that page. Its paint then calls `.has()` on the plain object at src/render/project-view.ts:218. This is deterministic once a reload occurs with marks; it is not a race in the writer. Leave the transient selection out of the reload handoff, or restore it as a Map if it is meant to survive.

3. `t` silently discards marks in Split Progress. src/render/workboard-input.ts:59–65, :223–229, :242–246 still runs Classic's `tryOnly()` on `t`, despite Split having no to-try filter. An owner using the Classic shortcut while on Split Progress loses the batch without leaving the visible view, the cursor jumps to the starting row, and the next Esc only clears the invisible filter. Keep `t` and the filter state Classic-only.

4. A brief whose inputs are known to have changed stays visible pending a replacement or after a refusal. src/collectors/try-brief.ts:97–107 starts a new request when the hash changes but leaves the previous result in `rows`; :116–123 checks only `r.text`. Correct the acceptance procedure in a named ticket without editing the STATE description and wait for the prescribed recheck. Even after the new hash has been computed, an in-flight or failed replacement leaves the old instructions on screen, contrary to 04's original-text fallback. Hide the old brief once a new input hash is detected. Also include the milestone in the ledger-line identity: moving the same ID and description to another milestone currently hits the old hash and display check despite changing the ledger line.

Can delete: src/render/project-view.ts:189–191 still carries Inbox's `number | boolean` compatibility branch and its comment; all three call sites now pass a number. Keep the saved-`inbox` fallback test, not that compatibility branch. `legendItem`, `legendGrid`, `HOME_TICKETS`, `HOME_WAITING`, `itemRight`, and `ticketLane` in project-view.ts, and `LEGEND`, `presetName`, and `placeRow` in control-view.ts, have no external callers; drop their `export` keywords, not the functions Split does reuse. The second-click fix can delete the duplicate activation path rather than add a separate mouse rule.
