## Findings

### 1. Blocked browser jobs become successful completions

`src/collectors/job-observations.ts:451` — The generic completed browse/judge fallback turns a persisted browser result of `blocked` into `outcome: completed` and `status: completed`.

**Severity: major.** `Agent.run()` stops normally on both `done` and `blocked`, and `runBrowse()` persists either through `complete()` (`src/jev/runtime/executor.ts:836–847`). Thus a real browser goal that cannot proceed produces `state: completed, result: {status: "blocked", ...}`. The collector loses that result and paints success. A real-file probe through the collector and composer returned `completed / completed / current` for this blocked result. The same fallback also accepts a malformed completed browse record with the `result` field missing, because `undefined !== null`.

**Suggested fix:** Reduce results by job tag, preserve the browser's literal outcome, and give blocked/non-success results a non-success effective status. Validate required result data before accepting completion; add blocked-browse and missing-result regression cases.

### 2. Expired Jev liveness remains current while the bounded scheduler catches up

`src/collectors/job-observations.ts:903` — Snapshot projection exempts every Jev job from live-deadline expiry, even when its last successful runtime corroboration has expired.

**Severity: major.** After collecting 150 running Jev jobs, I made the injected process probe report dead, advanced the clock by 20 seconds, and refreshed once. All 150 jobs still had `status: running` and `freshness.state: current`, despite their stored 15-second `liveDeadline` being in the past. Their generators had not yet reached the runtime check again. The scheduler's read bounds must not extend liveness indefinitely until each job gets another complete observation turn.

**Suggested fix:** At snapshot projection, demote non-terminal Jev jobs whose corroboration deadline has expired, preserving last-known evidence without additional I/O. Test expiry with enough real job files to require multiple refresh slices, not only a single job.

### 3. Closing a direct CLI job can resurrect running and erase its terminal outcome

`src/collectors/job-observations.ts:620–628` — The non-dispatch Herdr reducer ignores closure when selecting active status and discards the previously observed outcome when the receipt changes to `closed`.

**Severity: major.** A direct job observed as `failed/error`, then explicitly closed while the cached Herdr sample still says `working`, becomes `lifecycle: closed, outcome: null, status: running`. I reproduced exactly this transition through real association/receipt files and composition. Once that sample disappears, the failure remains lost and the row becomes unknown instead. Even an ordinary running-to-closed transition can retain a spinner from the pre-close list sample.

**Suggested fix:** Handle closure independently from outcome: a closed job must not derive running from a live sample, and closing must retain an already observed completed/failed outcome. Cover direct Herdr cleanup transitions as well as the existing Pi-dispatch cleanup test.

### 4. An unreadable QA file becomes a false empty request list on alternate scans

`src/collectors/job-observations.ts:720–722` — Returning early on an unreadable question or answer leaves the QA directory cursor open, so the next observation continues past the damaged entry and can report zero requests.

**Severity: major.** With a valid Pi job and one `q1.md`, making only that file unreadable produced successive snapshots with `requests: null`, `requests: []`, `requests: null`, `requests: []`, although the file remained unreadable throughout. On the second scan the existing cursor is already after `q1.md`, reaches EOF, and returns an empty list. This violates the required unknown-not-zero behavior; the current permission test only makes the directory unreadable and misses these early-return paths.

**Suggested fix:** Close/reset the directory cursor on every completed or aborted QA scan, including question/answer read failures, while retaining it only during a suspended incremental scan. Test repeated ticks with unreadable question and answer files.

### 5. A transient QA outage permanently poisons an otherwise absent report

`src/collectors/job-observations.ts:591–596` — QA failure changes a legitimately absent report from `available: false` to `available: null`, which subsequent observations interpret as evidence that a report disappeared.

**Severity: major.** Start a working Pi-dispatch job before it has written `report.md`: the row is current and report availability is false. Make `qa/` unreadable once, then restore its permissions. The row remains stale with `reason: report_unreadable` and effective status unknown on every subsequent observation, despite readable STATUS/QA and a matching live Herdr sample. I reproduced this recovery failure; there never was a report to lose.

**Suggested fix:** Keep QA and report availability independent. A QA error must not overwrite valid `available: false` report evidence, and an unknown report value must not itself establish prior report existence. Add a QA outage/recovery test before report creation.

### 6. Inactive helper history is advertised as a current question

`src/collectors/job-observations.ts:731–732` — Any helper's retained `waiting_orchestrator` lifecycle marks questions current, without checking the primary's active `helper_pending` relation or whether that helper evidence is stale.

**Severity: minor.** With the primary `working`, `helper_pending: null`, an old `review-1` STATUS still `waiting_orchestrator`, and a historical unanswered question, the collector returns `current: true`. This was reproduced through real STATUS and QA files. The existing `observeDispatch()` semantics deliberately consult only the helper named by `primary.helper_pending`; unrelated historical helpers must not manufacture current waiting evidence.

**Suggested fix:** Use the primary's explicit active-helper relation and valid current helper evidence when projecting current requests. Add inactive-helper and stale-helper waiting cases alongside the primary-state tests.
