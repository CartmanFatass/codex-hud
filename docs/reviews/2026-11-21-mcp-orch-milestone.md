## Spec — blocking

1. **04: Standard pi workers cannot call `hud_lease`.** The HUD extension registers it (`integrations/pi/package/extensions/hud.mjs:14–29`), but Fishpref `pi-roles/extensions/roles.ts:242–256` activates only the role allowlist plus the original four HUD tools. The shipped implementer, reviewer, architect and sonic allowlists do not include `hud_lease`. The `--tools` path in `pi-roles/bin/pi-role:130–140` also adds only the original four. A pi implementer told to take a lease cannot do so natively. Update both activation paths. The passing test at `tests/unit/pi-package.test.mjs:861` proves registration in a stub host, not exposure to a launched role.
2. **03: An unregistered checkout can supply standing worker instructions.** `thin-main.ts:1045–1062,1274–1276` takes the root from the project lookup but ignores its registration result. It adds the local reference or inlines the file into a browser brief automatically. The implementation follows the slice brief's “registered or not” wording, but ticket 03 says *registered* and `docs/spec.md:104` says an unregistered checkout's `.hud/` does nothing by itself. The test at `tests/unit/thin-mcp.test.mjs:3891` expressly asserts the conflicting behavior. Keep the existing setup gate or get an explicit owner exception to the spec; do not treat the updated reference docs as that exception.
3. **01/07: Launch facts are incomplete for CLI places and disappear from successful task-mode dispatches.** `packages/hud-mcp/src/launch-thinking.ts:10–12` returns no facts for any non-pi harness; `thin-main.ts:703–710,1406–1412` consequently forwards an unsupported CLI effort unchanged rather than mapping it before opening a tab. The tested pi fallback is not CLI preflight. Separately, the ordinary launch result contains `attempts`, `used_place` and effective thinking (`thin-main.ts:188–205`), but the successful task branch at `:2092–2093` discards that result. A Claude main session whose dispatch fell through sees a working handle, not the places tried or the failure cause. Honor known CLI capabilities (or explicitly narrow what is supported with the owner), and carry a compact launch outcome through the task reply.

No other scope expansion found. The one-day Home-card change was requested. I did not count the CLI turn-token requirement, the ten-minute derived-key window, or the recorded restart-recovery stop rule as defects. No chaining, project notes or resident service was added.

## Simplicity and quality — blocking

1. **07: The HUD's own CLI follow-up can strand a Claude task.** The supervisor advances `turn.json` when it sends the one-time sonic-collection prompt or asks a quiet worker to write its report (`packages/hud-mcp/bin/hud-cli.mjs:210–215,234–245`). The task fence is the exact CLI turn token (`thin-main.ts:1902–1907`); the next poll then terminally fails the only handle as “no longer current” (`:1928–1933`). No main-session send took place to create a replacement. The worker can collect its children, write a valid final report and close normally without a report wake. Keep the delivery handle through HUD-internal follow-ups while retaining the fence that prevents an old cancel from affecting a newer caller-initiated turn.
2. **07: A worker that needs intervention can leave Claude waiting silently.** A blocked CLI or one handed back by the supervisor (missing report, supervisor error, etc.) can have `blocked`/`waiting_orchestrator` with no `qN.md`. Ordinary `hud watch` treats these as immediate attention (`src/cli/watch.ts:60–70`); `sampleTask` only updates the working task's status text (`thin-main.ts:1935–1964`). Task clients have neither the ordinary change stream nor the Monitor hint. `/tasks` can display a reason, but this does not hand it back to the idle main session. Deliver actionable attention without failing or closing the worker.
3. **02/06: A Pi check hold prevents the promised repair after a report read.** `hud_read` stamps the read receipt (`thin-main.ts:1726–1734`). The watcher holds reaping *before* the Pi read-close path while checks are running (`packages/hud-mcp/bin/hud-watch.mjs:280–291`). The same settled job therefore remains `idle_grace` with a read report: `hud_send` returns `not_continuable`, since the repair branch requires an already-written `closed after report read` status and continuation requires an unread report (`thin-main.ts:1531–1549`). This lasts for the check run, not just a file-event race. If the native grace expires first, the worker can publish ordinary `settled` closure without the read-close reason. Keep the check hold for physical cleanup, but base repair on the same *current-settlement* read evidence as read-close, not on whether reaping has finished. Do not loosen the guard for old reports read during a newer turn.

### What can be deleted or folded

- Validate effective `pi_args` once after resolving request/place options, rather than keeping the reserved-flag regex in `placeOptions` and `launchPlace` (`thin-main.ts:1138–1143,1404–1405`). Keep the check for args supplied by the configured place as well as the caller.
- Stop writing both `message_keys` and `send_outcomes` for new sends (`thin-main.ts:1522–1524,1552–1559`). The outcome already has the exact key and delivery result. Keep a read fallback for old receipts and use the same normalized history for the watcher’s legacy read-close guard (`hud-watch.mjs:195`).
- Choose the immediate reply or task reply in one place. The `TASK_HANDLE` symbol and ordinary-result spreads currently build values the RPC layer discards; the launch-result fix is an opportunity to remove that plumbing. Keep the early question-delivery claim, the prompt receipt token, and the late-cancel protection.
