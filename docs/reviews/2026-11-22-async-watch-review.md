## Spec / brief — blocking

1. **A published watcher can still die on TERM/INT without cleaning up its PID marker.** `src/mcp/thin-main.ts:285–288` publishes `watch.pid` as soon as spawn returns, but `packages/hud-mcp/bin/hud-watch.mjs:19–24,523–524` awaits the dist lock and imports before installing handlers. If the owner stops the advertised PID while a build is publishing, Node takes the default signal exit and leaves `watch.pid`. This window can last up to the 15-second lock budget (`scripts/dist-lock.mjs:13–24`), not just a narrow check/unlink race. Don't advertise a watcher as ready before it can handle shutdown, or make startup itself handle TERM/INT and clean up its own marker.
2. **The zero-Decision-call guarantee stops at the last observed filesystem event.** `packages/hud-mcp/bin/hud-cli.mjs:286–297` rechecks the stop file after the pane read, but provider selection and cap reservation both yield before `src/mcp/quiet-decision.ts:88–106` starts the HTTP request. If the directory watch is unavailable (explicitly handled at `hud-cli.mjs:110–132`), a stop file published while reservation is waiting leaves the signal clear until the 30-second tick. A paid request can start with stop intent already on disk. Recheck that intent at the actual fetch boundary, including provider fallback; retain the signal for cancelling requests already sent.
3. **Antigravity delivery still blocks the worker and queue-watcher event loops.** `packages/hud-mcp/bin/hud-notify.mjs:84–91,109–110` and `src/cli/watch.ts:328–329` reach `spawnSync('flock', …)` at `packages/hud-mcp/bin/agy-events.mjs:20–31`. When an idle delivery holds the mailbox lock across its slow herdr prompt, another direct `hud_ask` for that pane can spend 250 ms blocking the worker MCP while acquiring it; the queue watcher can likewise be blocked before processing SIGTERM. This is the delivery mailbox, not the accepted lease/job-project S4 exception. Keep the same FD/claim semantics but acquire without blocking the event loop.

## Simplicity and quality — blocking

4. **An unexpected reap-leader exit drops ownership of a still-running helper group.** `src/roles/herdr-run.ts:65–70,132–135` settles and clears the watchdog on `close` whenever no stop was initiated by the runner. The current `pi-role-reap` waits for herdr with `spawnSync` and its own stdio pipes. If the reap leader is killed independently while that client hangs, the leader's pipes can close while herdr is still alive in its group. `packages/hud-mcp/bin/hud-watch.mjs:323–333` then removes the entry; a later watcher shutdown cannot drain it, and a retry can leave another client. Handle unexpected leader death as a group-cleanup path while ownership can still be established; don't fix this by unconditionally signalling a stale numeric PGID.
5. **A failed Pi read-close can stop retrying precisely when the worker still needs cleanup.** `packages/hud-mcp/bin/hud-watch.mjs:295–299,374–378,414–421` suppresses the observed tab close for a read-close retry, then skips the idle-grace job if that tab is closed and the recorded root is still alive. If the owner closes the tab during a slow read-close and the reaper returns incomplete with the root still running, the watcher polls forever but never retries that reap. Keep the protection against falsely marking the reaper's own tab close as failure, but retry cleanup of the same recorded owner after the retry deadline even when its tab is already gone. This is the retry contract in `docs/spec.md:98–103`.

**Delete:** `ensureQueueWatcher`'s unused `{ signal }` option and its abort checks (`packages/hud-mcp/bin/hud-notify.mjs:141–145`) unless a caller is given actual ownership of cancelling startup. Keep signal support for the awaited `paneInfo`/delivery calls.

## Optional — non-blocking

- `src/roles/herdr-run.ts:80–101`: the spawn API supplies a positive child PID, so there is no normal `-0`/`-1` target. After leader exit, the `kill(-pid, 0)` check and later KILL are not an identity fence: the old group can go empty and its ID be reused before escalation. Also, after KILL a wait for the leader's `exit` has no deadline if the kernel cannot terminate it. These are edge cases, not observed failures. The two direct `pi-role-reap` calls outside the watcher still kill only the leader on timeout, by the chosen group-policy scope.
- `packages/hud-mcp/bin/hud-watch.mjs:165–166,214–225,387`: checking `watch.pid` then unlinking is not atomic against another starter; the in-memory job/repo exclusions are likewise per watcher, not across racing starts. A stale quit marker plus a zombie/reused supervisor PID can also defer a tab verdict. Normal `/quit` marker creation (`wx`), STATUS publication, and cleanup are ordered correctly; these require a concurrent replacement or stale identity.
- The 250 ms Codex grace covers cancellation **in the queue child**, not the whole queue-watcher loop. For example, `src/cli/watch.ts:305` can await an uncancelled one-second `pane list` in `src/roles/job-project.ts:32`, and the lazy runner import can wait for the dist lock without a signal (`hud-notify.mjs:65–76`). That loader also caches a failed import/lock attempt indefinitely for a live MCP process. Consider reusing the startup import or not memoizing failures. This is separate from changing S4's flock.
- Add targeted coverage for a detached leader dying first with a live helper, lost directory-watch notifications at the paid gate, TERM during startup, and a failed read-close with the tab gone but the root still alive. The landed tests cover the healthy-watch and tracked-child paths; I did not execute them.
