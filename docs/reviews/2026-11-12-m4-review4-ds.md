## Findings

### 1. Major — a symlink loop in a job's `sessions/` kills the job watcher before its first scan, and the owner's real tree has one now

**Where:** `packages/hud-mcp/bin/hud-watch.mjs:215` (`fs.watch(jobs, { recursive: true }, …)` runs before `scan()`
at `:226`).

**What the owner sees:** no job watcher runs. Finished jobs' herdr tabs stay open (the watcher is what closes them,
spec §2.1), and the new retention never deletes a job directory. The job that retention should eventually delete is
the one whose link kills the watcher, so the tree cannot heal itself.

**Why:** Node's recursive watcher walks the whole `jobs` tree and calls `uv_fs_event_start` on each entry; a
self-referential `sessions/<session>.jsonl` link (target = its own path) gives ELOOP. The throw is synchronous,
before `watcher.on('error')` exists and before `scan()`. The process exits 1; the MCP's `ensureWatcher`
(`packages/hud-mcp/src/thin-main.ts:195-209`) then reads the dead pid and starts another one that dies the same way.

**Evidence (real tree, read-only):**
- `~/.hud/jobs/j1e60fa6ea5b3a613/sessions/2026-11-12T20-10-27-448Z_01a1d162-…jsonl` is a symlink to
  itself. It was created 20:10:27 UTC, four minutes before pi-roles `27e2006` added the self-link guard; the job is
  `failed` (`exit_reason: error`, pi's first session write failed), has no `reaped_at`, and records `TAB=w4E:t2G`.
- `~/.hud/watch.log`: last `exit` at 20:08:24; since then 8 `start` lines (20:14:34, 20:28:07, 20:28:11,
  20:31:28, 20:49:18, 20:57:34, 20:57:37, 21:06:52) with no `exit` and no `watch error` line. The 20:10:25 watcher
  ran one scan (32 deletes) and then vanished when the link appeared.
- `ps` shows no `hud-watch.mjs` process; `~/.hud/watch.pid` holds 2910716, which is not alive.
- Fresh reproduction with the reviewed watcher in a temporary home (same job shape): exit 1, stderr
  `ELOOP: too many symbolic links encountered, watch '<job>/sessions/x.jsonl'`, `watch.log` contains only `start`,
  the expired job was not deleted.

**Smallest fix:** make the watcher survive a bad tree: wrap the `fs.watch` call in `try/catch`, log
`watch error: …`, and still run `scan()`; in the scan, unlink self-referential `sessions/*.jsonl` (and
`.dispatch/*/sessions/*.jsonl`) links — a link whose target is its own path can never resolve, so removing it loses
no data — then retry the watch once. Guard `watcher?.close()` in `stop()` and the error handler. Immediate unblock
for the owner: remove the job directory `~/.hud/jobs/j1e60fa6ea5b3a613`.

This is not introduced by the RETENTION-SAFE/M4-FIX3 diff, but the trigger comes from this milestone's SESSION-LINK
migration window (`docs/handoff/STATE.md:26`) and the watcher is the component the milestone relies on to close tabs
and run retention; the owner would install the release into exactly this state.

## Optional (does not change the verdict)

- `packages/hud-mcp/bin/hud-watch.mjs:108-122` — `preserveSessions` follows a symlinked `sessions/` directory
  (`existsSync`/`readdirSync` resolve it), so real files in the linked target are renamed into pi's store. No tool
  creates such a directory and the bytes are preserved, but the watcher then mutates a directory outside the job.
  Fix: `lstatSync(folder).isDirectory()` without following links, or skip a symlinked folder.
- `packages/hud-mcp/bin/hud-watch.mjs:118` — the store directory uses `cwd.slice(1).replaceAll('/', '-')`, while pi
  uses `replace(/[/\\:]/g, '-')`. A session whose cwd contains `:` or `\` is preserved in a directory pi will not
  list (no loss). Fix: mirror pi's regex.
- `packages/hud-mcp/bin/hud-watch.mjs:115` — the whole session file is read to parse its first line; a large legacy
  session costs a full read per expired job. Fix: read a bounded prefix (pi caps its header scan at 1 MiB).
- `docs/ARCHITECTURE.md:1024-1026` and `README.md:206-207` still advertise `npm run test:integration`,
  `test:visual` and `test:visual:update`, none of which exist in `package.json` (pre-existing; the round-3 note's
  README `test:integration` line was removed). The owner following §9 gets "Missing script".
- `packages/hud-mcp/bin/hud-watch.mjs:174-199` — the reap-then-delete path records `reaped_at = now`, not the
  recorded close time, so a job whose tab closed while the watcher was down is deleted up to a day later than the
  owner's "one day after closing". Delay only, not data loss.
- `packages/hud-mcp/bin/hud-watch.mjs:110-124` — a partial move (one file moves, a later one fails) leaves the moved
  file out of the job directory while the job is kept; no loss, but the panel's session readers see fewer sessions
  until the job is deleted.
- `docs/ARCHITECTURE.md:79` — says each job's `sessions/` holds links so deleting a job does not delete history; it
  does not mention the pre-delete move of legacy real files (the reference does).
