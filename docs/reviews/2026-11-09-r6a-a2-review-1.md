## Findings

### 1. Strict Codex admission can bind a caller to another session's pre-existing connection

**`src/collectors/daemon-binding.ts:168–170` — Severity: major.** Strict mode treats uniqueness inside the startup window as ownership evidence without checking whether the selected daemon connection predates the calling TUI.

Concrete scenario: session A opens daemon connection 1 at `t=900`; TUI B (`pid=10`) logs startup at `t=1000`, but has no logged attributable startup request; A resumes its thread on connection 1 at `t=1001`. The bounded candidate window sees only B's startup and A's resume. `findConnection({ pid: 10, since: 1000, strict: true })` returns connection 1, and `latestThread` returns A's thread. Role admission therefore grants B A's source-qualified session identity rather than returning `identity_unverified`, allowing cross-session selection/job access.

I reproduced this twice against the real compiled collector with an in-memory native SQLite store. Both runs returned:

```json
{"connection":{"server":"daemon","id":1,"from":{"ts":1000,"nanos":0}},"thread":"synthetic-A-resumed"}
```

**Suggested fix:** In strict mode, establish the exact connection's earliest logged request of any kind without the startup-window lower bound; require that it does not predate this TUI and that its first request is a corroborated `codex-tui` thread/start or thread/resume. Refuse earlier or unestablished/bound-exhausted history, preserve display behavior, and add the foreign-connection regression alongside the normal single-TUI case.

The orchestrator confirmed this is actionable in review question **q4**: q3 authorized strict attribution, not a unique-but-known-pre-existing connection.
