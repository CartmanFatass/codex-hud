### 1. Major — bootstrap import failures let HUD commands reach the provider

**`integrations/claude/scripts/hook.mjs:1`** — The static binding-module import executes outside the error handler, so a missing/broken cached dependency exits non-blockingly and Claude proceeds with model expansion.

A missing `scripts/binding.mjs` therefore bypasses the intended local-failure block. I reproduced the equivalent unresolved static import in a private copy of the materialized plugin, using Claude 2.1.319 and the recording localhost provider. Plugin validation still exited 0, but the resulting request counts were:

```text
canonical: 6
alias:     6
setup:     6
ordinary:  6
```

Each HUD command ended in the fake provider's synthetic HTTP 400 instead of a local blocking response. This violates the explicit requirement that local failures remain blocked; the Markdown command bodies do not provide that guarantee. The existing successful smoke and mutation tests do not cover bootstrap failures.

**Suggested fix:** Load the binding dependency inside the guarded block and emit the blocking response on import failure. Verify the failure policy for hook startup/nonzero-exit/timeout failures, and add a real-CLI negative-control test proving zero provider requests with a missing bootstrap dependency.

### 2. Major — an unavailable parity inventory disables rollback and unrelated integration functions

**`integrations/claude/scripts/binding.mjs:26`** — Eagerly requiring the parity inventory to exist makes statusline restore depend on parity, before `setupCommand` can take its parity-independent restore branch.

Concrete reproduction through the actual copied `scripts/hook.mjs`:

1. Created synthetic settings/configuration and a valid parity inventory.
2. Ran setup preview and apply through the plugin bootstrap; both exited 0 and produced a valid backup.
3. Removed only the inventory file.
4. Ran setup restore with that backup through the same bootstrap.

Actual result:

```text
plugin restore: exit=2
reason: HUD unavailable: invalid binding or hook failure.
settingsRestoredByPlugin: false
```

Calling `setupCommand(['restore', '--backup', backup], ...)` directly then returned `DONE` and restored the exact original settings. The existing test exercises only that direct route, masking the bootstrap defect. The same eager check also prevents the MCP adapter and panel hooks from loading when an unrelated parity file disappears.

**Suggested fix:** Validate/read the optional inventory only in the parity-dependent preview/apply path. Add bootstrap-level restore and MCP tests with the bound inventory absent or unreadable.
