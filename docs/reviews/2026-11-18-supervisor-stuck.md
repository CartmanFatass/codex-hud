2. Cause, propagation and limits

• Dispatch waits for agent start/readiness, writes turn.json just before prompt, then starts the supervisor after prompt submission (packages/hud-mcp/src/thin-main.ts:682–725; cli-judge.ts:34–47). Interactive readiness is not completion of all launcher forks. workerHasChild walks every thread's child list, checks PPID, start ticks and worker identity; on an older child it pushes the PID and continues down, on a qualifying descendant it returns true. It does not test who initiated that subprocess or whether it is performing a task (cli-judge.ts:50–118). This is a false positive that lasts as long as the qualifying infrastructure lives in the same turn, not literally forever. Identical server setup can settle if startup finishes before the send. A later turn normally excludes those existing PIDs but a late/lazily launched or restarted server can affect later turns too.
• Judge checks for a new report relative to the send baseline, non-working status and a stability window (2 s at trusted end, otherwise 10 s; longer on outage), then requires a negative child sample BEFORE publishing output_written, starting grace, or closing a read report. With no report a positive sample also defeats a quiet decision. Unknown/incomplete scans are conservative, not proof that work is done (cli-judge.ts:170–175,198–225). An unread finished report in this job should have entered grace, not closed merely because its file existed. Reading it alone would not have cleared the false positive.
• No independent missed-event explanation is needed. The per-job supervisor subscribes to pane status/lifecycle, normalizes dotted event names, guards seeds by generation, watches report/receipt/turn/QA, reconnects after loss, and on the 30 s safety tick independently calls agent.get and samples children when not working. A due settlement requests a sample even between ticks. Every correct idle refresh would reproduce the same false positive. STATUS is atomically renamed only if its public row changes; updated_at is not a heartbeat. Report signature, sampled child and internal quiet clock are not public fields (packages/hud-mcp/bin/hud-cli.mjs:59–102,103–160,162–197,237–252; herdr-request.mjs:4–18). I did not instrument the real event stream or count this PID's ticks.
• thin-main.readRow uses jobRow, not a fresh Herdr opinion. idle_grace/closed are displayed as done, working as working; report_present/unread are computed separately from file/mtime/read_at. Reading one job with no wait can return its report while working, and returning the body stamps it read for the main session; listing doesn't (thin-main.ts:731–755,764–802,1066–1104; src/collectors/thin-jobs.ts:176–239). MCP changes and verbose watch suppress working→working report-only flips; ordinary hud watch does not emit working-report completion or catch it up; it emits actionable events. That explains the silent monitor and the contradictory-looking row without a second completion bug. Do not convert 'report_present' to 'done' in any of these readers (thin-main.ts:1197–1213; thin-jobs.ts:243–281,289–328; src/cli/watch.ts:27–60,190–205).
• The earlier design explicitly wanted to detect agy → bash → background command, and the re-review intentionally preserved real new grandchildren below old helpers. Its tested 'old helper' case and the new live tree are different. The assumption that all session infrastructure starts before the first send, not the owner's distinction between infrastructure and work, is what failed. See docs/spec.md:11–13 (§2.1); .scratch/worker-close/issues/01-live-child-is-working.md:6–20, 02-close-on-read.md:6–18, 03-review-fixes.md:8–22; docs/reviews/2026-11-17-worker-close-review.md:11–14,39–53.

3. Other state faults, independent of the live pin

A. Two writers disagree about an explicit stop racing tab closure. judge gives the stop marker priority even over worker death and tab close (cli-judge.ts:174–182). The global watcher instead unconditionally writes failed/tab closed for a still-nonterminal row on tab.closed, without checking the marker, report or PID; the per-job writer then refuses to replace that verdict (hud-watch.mjs:208–214; hud-cli.mjs:169–178). With a temporary jobs root, fake socket that pushed tab.closed, fresh report.md, STATUS=working and an existing STATUS.json.stop-requested, running the actual hud-watch.mjs produced:
  {"state":"failed","output_written":false,"exit_reason":"tab closed","ended_at":"2026-11-18T08:46:25.277Z"}
The same stop+tab+report facts passed to judge produced stopped. Without a stop marker, judge also distinguishes PID gone with fresh report (closed) from tab closed with PID still alive (failed); the watcher bypasses that distinction. This can turn an intentional close into a red failure and a two-hour retention, not what happened in the final target receipt. Repair: use the same terminal-fact ordering and fresh turn-relative report test for CLI tab-close in both writers. Test both writer orders with stop+close and with independently confirmed exit+report, plus genuine tab loss without output. Keep failure for genuine loss, not for a stop.

B. A failed quit and failed cleanup need not leave any supervisor retry. hud-cli.mjs:27–32,237–245 discards the exit status of /quit, writes closed and shuts down. I ran the actual supervisor against a fake idle Herdr socket, read report, private temp job, synthetic live worker and a private herdr executable that always exited 1. Output:
  fake-herdr: agent prompt fake /quit => exit 1
  supervisor exit 0 STATUS closed closed after report read worker still alive true
Closed is a lifecycle result; it is NOT proof the process/tab has gone. Normally the global watcher then calls pi-role-reap and stamps reaped_at only on success. If terminal reap fails, it only warns; with no other open job/deadline it can exit rather than retry (hud-watch.mjs:272–326). This latter consequence is from code; my probe deliberately did not start a real reaper. It generalizes the already recorded Pi partial-cleanup follow-up (worker-close review:45–55). Repair separately: keep a failed terminal reap pending on the existing slow timer until cleanup succeeds or ownership no longer matches; don't start a second killer or report task failure for a cleanup error. Test '/quit rejected, reap fails once, next slow tick succeeds' with no unrelated file events. Distinguish worker settled from cleanup confirmed in any diagnosis.

C. Rejected continuation can manufacture a new working turn. thin-main.ts:1120–1165 records the attempt and calls writeTurn BEFORE agent prompt, correctly protecting fast output, but even a definite no-input rejection returns send_failed with the new seq and old report as its permanent baseline. judge resets on new seq. Code-path replay with unchanged report R: “idle_grace true -> working false -> decide”. The judge result was measured; a historical real rejected prompt causing this was not observed. Keep the attempt/idempotency record. For a definite pre-input rejection cancel that provisional turn / restore prior settlement if still the same attempt; for ambiguous delivery keep the conservative baseline and hand off rather than guessing. Test failed send from unread idle_grace, and separately an ambiguous response after a fast successful report. Not a reason to move writeTurn after every successful send.

Display limitation, not a new producer fault: a temporary row waiting_orchestrator, blocked=false, reason='supervisor exited; worker still running' yielded “raw,display: waiting_orchestrator working catch-up: []” using jobRow and watchCommand(['--all']) on a fresh monitor. A live transition is delivered; attaching afterwards is different. This matches the enumerated catch-up policy (src/cli/watch.ts:45–60; packages/hud-mcp/README.md:104–109); raw state and reason remain available via MCP. No reader rewrite recommended for the incident.

4. Fix proposal and tests

Recommendation: keep the judge, tick and report-read semantics. Change what counts as positive process evidence, narrowly enough not to lose a worker's real background command. Age + ancestry alone cannot distinguish 'old helper started its server' from 'old helper started my build': the synthetic example is the same kernel tree in both interpretations.

1 — For a deterministic fix of the observed case, teach the CLI process walk about the bootstrap chain, not a list of process names to ignore everywhere. At the existing sample in hud-cli.mjs:141–159 pass CLI/first-turn context to cli-judge.ts:69–117. While traversing a PID/start-verified direct launcher that predates first input, recognize the actual known MCP launch chain: npm exec for the server package → its matching sh -c entrypoint → that server; for the observed DevTools chain also its own packaged telemetry watchdog under that server. Exempt only the matching bootstrap processes as positive work evidence; CONTINUE walking their children. A different child, shell command, test runner, browser job, or new launcher started by the worker after input must still hold the turn. Match parent/entrypoint relationships, not 'node', 'npm', 'mcp' substrings or all descendants of those processes. If identity/shape is unrecognized, do not waive the hold. Use the same classification for settle, decide and auto-close through the existing single sampleChild path. No changing the CLI's configuration. Preserve the Pi caller (hud-watch.mjs:281–289) by keeping its current default unless separately qualified.

This is the smallest deterministic exception I would ship without relaxing protection for work through an older helper. Cost: bootstraps are launcher-specific; new wrappers, deferred direct MCP starts after input, or a future changed watchdog may still pin conservatively. The exemption is a positive identification of known startup, not proof of intent for arbitrary processes. If the owner wants a generic rule instead, make the trade-off explicit:

2 — Make first dispatch wait for positive session-helper startup completion BEFORE writeTurn and prompt (thin-main.ts:682–711), if a harness can expose that fact; then keep the current walk unchanged. This avoids vendor process classification and cannot erase real commands started by prompt. I found no such all-servers-ready guarantee in the dispatch path. A bounded pre-prompt wait for launcher children / a stable process tree can mitigate this run, but costs latency and is still a race; don't present a fixed sleep or a baseline moved AFTER input as a fix. Owner-side direct server entrypoints in place of npm bootstraps might reduce this specific window; not a required config change and not verified here.

3 — Simplest topology change, weaker contract: on the first turn do not descend into pre-input direct branches (or prune only identified pre-input MCP launcher subtrees). That fixes this live tree with very little code and still counts agy → newly started bash → sleep and a newly started direct npm job. It also hides genuine new work initiated THROUGH a pre-existing shell/service, including MCP tools launching subprocesses in a pruned subtree. The re-review explicitly valued that case. I would take this simplification only if the owner accepts that blind spot. A post-send grace window, ignoring all grandchildren, requiring a child to burn CPU, or letting a read report override positive work evidence can close a real background job; not recommended.

Acceptance: extend the real /proc fixtures in tests/unit/thin-mcp.test.mjs:753–777,925–992, not just a boolean judge table. Fake a pre-turn launcher, delay the matching shell/server/watchdog until after send, keep them alive, publish a report and idle status: unread → idle_grace with output_written; read → closed/reaped within one tick while the infrastructure was still present at preflight. Same setup plus a real in-turn sleep (a) direct / under a new shell, (b) under the existing helper/server: remains working despite report/read, no quit or quiet decision; after sleep exits, settles without waiting for the MCP server. Also no-report + infrastructure-only reaches normal handoff/decision; a genuine in-turn runner with the same executable name is not exempt. Retain existing tests for pre-turn child, fresh report, missed push and Pi read-close. Verify row/watch changes by observing working → idle_grace/closed, not by teaching readers to derive state from a report. Separate tests for A–C above. No build or fix performed.
