## Spec

### 1. `hud_roster` reports expired exhausted marks, so it disagrees with `hud_create` — major

`packages/hud-mcp/src/thin-main.ts:772` — `[...found.roles().values()].map(found.assignment)` passes the array
**index** as `assignment`'s second parameter (`nowMs`, added in 5b0d5b37), so the roster evaluates every mark at
`0, 1, 2, …` ms since epoch and `readExhausted` never drops an expired one.

Failure: a place was marked exhausted at 10:00 (one-hour TTL). At 12:00 `hud_roster` still returns
`runs_on: <fallback>` (or `available: false` when the last place is marked) while `hud_create` — which calls
`assignment(definition)` with the default `Date.now()` — dispatches the primary place. Reproduced end-to-end against
`packages/hud-mcp/bin/hud-mcp.mjs` with a temp `HUD_HOME` and one mark expired two hours earlier:

```
hud_roster imp.runs_on = cli | exhausted = ["pi:openai/gpt-6.1-sol"] | available = true
```

and at registry level, `.map(reg.assignment)` vs `reg.assignment(role, Date.now())` for the same role:

```
as hud_roster does (.map(assignment)): [{"role":"imp","runs_on":"cli","exhausted":1,...},{"role":"reviewer","runs_on":null,"exhausted":1,"available":false}]
with a real now:                      [{"role":"imp","runs_on":"pi","exhausted":0,...},{"role":"reviewer","runs_on":"pi","exhausted":0,"available":true}]
```

The convention tells the main session to call `hud_roster` before dispatching, so this is the wrong answer on the
first call after any quota failure + 1 h. The Control plane (which passes a real `now`) shows the place as
available, so panel and MCP also disagree.

Fix: `roles: [...found.roles().values()].map((role) => found.assignment(role))`.

### 2. `docs/reference.md` / `docs/reference.zh.md` still document the removed CLI-supervisor behaviour — major

`docs/reference.md:141-147`, `docs/reference.zh.md:108-111` — the reference says "A dead supervisor fails the job"
and "Herdr `idle` or `unknown` is an exit only when the agent is gone"; SUPERVISOR 08 removed both (a dead supervisor
with a live worker is `waiting_orchestrator`; herdr status is advisory and never ends a job). `docs/reference.md:134`
and `docs/reference.zh.md:102` still say a blocked CLI "sends one notice naming the job and pane", but the
supervisor's `notifyBlocked` was deleted (SUPERVISOR 07/08) — `changes` and `hud watch` are the only announcers.
Neither reference mentions `hud watch` (absent from the "Universal CLI and MCP" block, `docs/reference.md:64-72`),
`changes` in MCP responses, or the quiet-job decision.

Failure: the owner reads the reference and expects a dead supervisor to fail the job (so the session re-dispatches),
and expects blocked/quiet CLI jobs to announce themselves — the exact confusion this milestone exists to remove
("why can I see the failure on the panel and statusline but you don't know"). The shipped behaviour is the opposite,
and the one command that closes the gap (`hud watch` under Monitor) is undocumented.

Fix: rewrite that paragraph to the shipped rules (only pid/tab/pre-input rejection end a job; dead supervisor →
`waiting_orchestrator`; report settles at turn end after 10 s quiet; quiet past grace gets one Decision API choice),
drop the notice sentence, and add `hud watch` + `changes` to both languages.

### 3. §8 outbound-input rule: the quiet-job decision sends the worker's pane text to the Decision API, unlisted — major

`docs/reference.md:545` ("Outbound material") and `docs/reference.zh.md:402` — `ARCHITECTURE.md` §8 requires
"List every new outbound model input here and in both reference languages". `packages/hud-mcp/src/quiet-decision.ts`
sends the last 60 pane lines (≤12,000 chars) plus job state, background-child flag, minutes quiet, role and agent to
the Decision API provider; no row in either table lists it, and the feature is not described anywhere in the reference.

Failure: a CLI worker's terminal can show file contents, paths and secrets; the owner has no way to learn from the
reference that a quiet job ships that screen to a model provider. The Settings section also never says the
`quiet-job` counter exists.

Fix: add one row to both tables (e.g. "Quiet-job decision | Last 60 pane lines (≤12,000 chars), job state, background
child, minutes quiet, role, agent, prompt-already-sent; once per quiet episode, ≤3 per job") and a short paragraph in
the CLI section.

### 4. `docs/releases/0.1.4.md` describes the wrong `oracle` and omits `pro` — major

`docs/releases/0.1.4.md:17-19` — "`oracle` merges ChatGPT Pro, Gemini, and AI Studio Argon as ordered `bro` places".
Shipped `packages/hud-mcp/roles/oracle.json` is `cli claude fable → pi architect` (local, read-only) and the browser
role is `pro` (ROLE-BIND 05, `98f22d7d`), which the notes never mention. The notes predate that commit, as the brief
warns, but they are the release announcement the owner reads.

Failure: the owner reads the 0.1.4 notes, dispatches `oracle` for a web question, and gets a local claude job on
`fable`; `pro` is undiscoverable from the notes.

Fix: replace that sentence with `oracle` = local `cli claude fable → pi architect` advisor and `pro` = the browser
role (ChatGPT 6 Pro → Gemini → AI Studio Argon), and add the quiet-job decision and `hud watch` while the notes are
being touched.

### 5. Reference and skill claim `imp`/`reviewer` CLI fallbacks that do not ship — major

`docs/reference.md:108-110`, `docs/reference.zh.md:88`, `integrations/skills/hud-delegate/SKILL.md:29-30` — all three
say shipped `imp` is `pi implementer -> cli agy` and `reviewer` is `pi reviewer -> cli claude`. The shipped role files
have a single `pi` place each (`packages/hud-mcp/roles/imp.json`, `reviewer.json`), and
`.scratch/role-bind/issues/01-roles-and-places.md` records that as deliberate ("shipped `imp` and `reviewer` run on pi
only (fallbacks are the owner's)"). `packages/hud-mcp/README.md` has it right.

Failure: with `pi-role` missing from PATH, `hud_create(role: "imp")` returns `no_available_place` although the
reference and the skill promise an agy fallback; the main session concludes the role is broken instead of choosing
`on: "agy"`.

Fix: say `imp`/`reviewer` ship `pi` only and that a fallback is the owner's own `$HUD_HOME/roles` file (as the
`ownImp` test fixture does).

## Simplicity and quality

### 6. The Control plane help note is not translated — minor

`src/render/workboard-i18n.ts:228` keys the note as "…under the cursor (**/** types a model, r refreshes model
lists)…", while `src/render/work-view.ts:64` renders "…under the cursor (**m** picks a model, r refreshes model
lists)…". The keys differ, so `t()` falls back to English and a Chinese panel shows that help note in English
(§8: "Panel words go through `t()` with EN/ZH entries"). Fix: make the ZH key identical to the English string.

### 7. A settled card keeps showing its last quiet decision — minor

`src/render/work-card.ts:150` — `workCardDetail` prepends `quietDecisionSummary(worker.quietDecision)`, and
`quiet_decision` is never cleared from STATUS (`packages/hud-mcp/bin/hud-cli.mjs` keeps it in `current`). A job that
got a `still-working` (or `prompt-report`) decision and later settled shows "still-working 90% → wait · <result>" as
its third line, i.e. a stale "what it is doing now". Fix: only use `quiet_decision` while the job is unsettled (or
while its state is `waiting_orchestrator`).

### 8. `reportPromptSent` is per supervisor process — minor

`packages/hud-mcp/bin/hud-cli.mjs` (the `reportPromptSent` flag) is not persisted, so the "once per job" rule of
ticket 10 holds only within one supervisor run. A supervisor that dies after sending the fixed report prompt and is
respawned by `hud_send` can send it again on the next quiet episode. Fix: record it in STATUS (or in `turn.json`)
and read it back at start.

## Optional (non-blocking)

- **`hud watch` polls instead of watching files.** `src/cli/watch.ts` uses a 2 s `readThinJobRows` poll; ticket 03
  asked for "watching the job files the way `hud-watch.mjs` does", and the owner rejected 2 s polling for the
  supervisor's cost. Per poll that is one `readdir` of `jobs/`, one `lstat` per job (≤200), plus `lstat`+read of
  `job.json`/`STATUS.json`, `readdir qa/` and `stat report.md` per job — roughly 350 syscalls per poll for 50 jobs,
  forever, while the main session waits. Correct, but the cost is the one the design avoids elsewhere.
- `m` does nothing on a place whose harness lists one model (`chatgpt` "6 Pro", `grok-4.7`): `pickable` requires
  >1 model, so there is no way to type a model id there.
- `hud watch` with neither `HERDR_PANE_ID` nor `--all` prints nothing forever instead of saying no pane was found.
- The `prompt-report` failure path writes `turn.json` before the prompt, so a failed prompt makes the next wake a new
  turn and the job returns to `working` instead of staying `waiting_orchestrator` (bounded by the 3-question cap).
- `sessionRows()` re-reads every `job.json` (and each session job's STATUS/qa/report) on **every** MCP response with
  no signature cache; the panel has one.
- `hud_read`'s wait loop `continue`s without sleeping when the lightweight row is ready and the full observation is
  not (pre-existing, rare race).
- `dispatchCli` treats any `timeout|timed out` text from `herdr agent prompt` as "submitted"; a genuine pre-input
  timeout then leaves an unsupervised job in `working` until the idle grace instead of failing it.
