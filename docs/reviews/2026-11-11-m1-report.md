# M1 milestone report (2026-11-11)

M1: the owner installs the HUD and uses it from Claude Code, Codex and pi (spec §5). Written by the orchestrator per
the orchestrator brief §F.

## Demo (run for real on the owner's machine)

- `./install --with claude,pi,codex` registered the MCP and skill in all three clients. The Claude statusline is
  `hud-statusline`. The pi footer replaces p10k-footer. Settings files that are symlinks into the owner's config repo
  stayed symlinks.
- Dispatch from Claude (native `hud_create`), Codex and pi: a sonic job opens its own herdr tab, writes `report.md`,
  pushes `DONE` to the caller's pane, and `hud_close` reaps it. The owner saw "sonic 已就绪" from Codex and pi.
- `hud panel` inside herdr opens the panel in a split to the right of the caller. pi `/hud on|off` does the same.
- The panel's Home lists the session's jobs in the approved HOME-VIS4 layout: task title, model, state, open
  questions and answered ones. Finished jobs leave the list after 10 minutes and stay in the day's count.

## How it works now (ten sentences)

1. `./install` builds the repo, links `hud` and `hud-mcp` into `~/.local/bin`, and runs one script per chosen client
   in `install.d/`. `hud uninstall` reverses this and keeps the data.
2. Each client registers the same MCP server, `hud-mcp` with `HUD_MCP_SURFACE=roles`. It speaks JSON-RPC over stdio
   and offers six tools.
3. `hud_roster` lists the roles and the dispatch convention in effect. Each role is a small JSON file: the shipped
   defaults, or one in `$HUD_HOME/roles/`. The convention is one text file: the project's, else `$HUD_HOME`'s, else
   the default.
4. `hud_create` writes `$HUD_HOME/jobs/<id>/job.json` and `brief.md`, appending the report path. It then runs
   `pi-dispatch` from the locally installed pi-roles, which opens a herdr tab and starts the mapped pi role.
5. The worker writes `STATUS.json`, questions in `qa/`, and `report.md`. When it settles, pi-dispatch pushes one
   `DONE` or `FAILED` line into the caller's pane.
6. `hud_read` reports a job's state, report and open questions. `hud_respond` writes an answer file once.
   `hud_send` continues an implementer during its idle grace. `hud_close` runs `pi-role-reap`.
7. The `hud-delegate` skill lets the owner delegate in plain words ("派个 sonic"). The main session writes the brief,
   dispatches, waits for the DONE line, reads the result and decides the next step. The HUD never chains roles.
8. The panel is a TUI. It reads the job directories directly, so it needs no service and no database, and renders
   Home and Work.
9. Claude's statusline and pi's footer are ports of claude-hud and p10k-footer. They are now ours and are changed to
   our needs without tracking upstream.
10. Nothing proves identity or process ancestry between local processes. The threat model is one user on one machine
    with trusted configs (spec §4).

Nouns not in the spec:
- *request_key* deduplicates a retried `hud_create`, so an uncertain launch does not start twice.
- *idle grace* is pi-roles' window in which a settled implementer can still take a repair prompt.

## What went wrong in the flow, and the change

- Two install bugs (I1, I2) passed tests that only checked mocks. They surfaced on the first real install. The
  real-install step stays part of each milestone.
- The first trial-fix job was one imp with a 250-line budget that counted deletions. It stopped correctly at the
  budget. Budgets now count added lines only, so deleting old code is free.
