## Findings

### 1. Helper session identity is not revalidated when STATUS changes in place

**`src/core/materials/job.ts:920`** (also `:548–550`, `:833`) — Revalidation checks contributing file inode/ancestor chains but never checks that the current helper STATUS still names the helper session recorded in provenance. **Severity: major.**

Concrete scenario: admit `review-1.md` from helper session `original-helper`, save its annotation, then overwrite `.dispatch/review-1/STATUS.json` in place with a valid STATUS naming `replacement-helper`. The inode remains unchanged. The old envelope still passes `revalidateMaterials`, and a fresh authority/store restores the old annotation after restart. This violates the exact contributing-helper slot/session fence and permits stale helper evidence through the send/publication/persistence checks. The existing replacement test uses an atomic rename, so it only exercises the inode fence.

Independent production-path probe returned:

```text
helper replacement preserved inode: true
old helper envelope still authorized: true
old helper note restored after restart: true
```

**Suggested fix:** Revalidate each contributing helper's derived STATUS locator, validated slot/role/output, and exact session ID during both live validation and restoration. Add an in-place STATUS replacement regression, including store restart.

### 2. The supplied budget does not cover authority reads or metadata probes

**`src/core/materials/job.ts:307–310`** (also `:164–177`; `src/collectors/job-public-output.ts:76`) — Each authority JSON read creates an independent budget, while path/fstat probes are outside the caller's budget, so the material boundary can perform I/O after the caller's allowance is exhausted. **Severity: major.**

Concrete scenario: warm an authorized fixture, append only a newline to primary STATUS, then build with a supplied budget of zero files and zero bytes. The supplied counters remain zero, but authority validation reads the changed STATUS body and performs hundreds of path probes. The adapter only starts using the supplied budget after its authorization/source checks. There is also no caller-budget metadata counter/limit, and `fstat` calls are not included in `jobFileMetrics.probes`.

Independent probe returned:

```text
supplied budget charged files/bytes: 0 0
actual additional authority body reads/bytes: 1 508
actual metadata probes despite zero read budget: 260
```

The last value is the existing path-probe counter, not a complete fstat-inclusive I/O total. This is a P3a accounting/enforcement defect, not a request to implement P3b's panel scheduler.

**Suggested fix:** Thread one supplied budget through policy/source admission, JSON reads, path checks, pinning/revalidation, discovery, and extraction; charge every file/byte/metadata operation and honor its deadline. Test the combined authority-plus-adapter path, including a 64-probe allowance.

### 3. A transient budget shortage becomes a permanently cached no-material denial

**`src/collectors/job-public-output.ts:310–317`** (also `:122–125`, `:194–195`; `src/core/materials/job.ts:744`) — Budget exceptions are treated as unavailable sources and the resulting incomplete reduction is cached under the normal unchanged-source signature, preventing later calls from completing extraction. **Severity: major.**

Concrete scenario: on a cold, authorized job, supply a one-file budget. STATUS consumes that file; all material reads are deferred by the budget. The adapter nevertheless caches the empty reduction, and `buildMaterials` returns `no_material`. Retry immediately with a fresh full budget and unchanged sources: the cached empty reduction is returned again without another read. The job remains denied until unrelated source/policy changes invalidate the cache. Partial reductions can similarly remain incomplete indefinitely.

Independent probe returned:

```text
one-file first result: {"denied":true,"reason":"no_material"}
full-budget retry result: {"denied":true,"reason":"no_material"}
retry performed no more reads: true
```

**Suggested fix:** Distinguish budget deferral from confirmed missing/invalid sources, preserve a resumable extraction cursor, and expose pending/partial rather than authorization/no-material failure. Do not cache budget-deferred absence as a completed unchanged reduction; test completion across successive bounded calls.

### 4. Unchanged material refreshes still rehash public content

**`src/core/materials/job.ts:737–790`** — The adapter's reduction cache avoids body reads, but every unchanged `buildJobMaterials` call rebuilds the envelope and hashes every fragment and aggregate again. **Severity: minor.**

Concrete scenario: warm the adapter, leave all policy/source/selection inputs unchanged, then perform the five refreshes used by the cost test. Instrumenting the real `crypto.createHash`/`update` calls records **35 hashes**, including **20 updates containing the unchanged public-output sentinel**, despite no additional adapter reads. The current cost test only asserts body-read/parse counters, so it misses the brief/q2 zero-hashing requirement. No production polling loop is wired yet, which limits the present impact.

**Suggested fix:** Reuse a bounded, immutable prepared envelope/content identity while authorized source revisions and selection are unchanged, without weakening send-time authorization. Extend the unchanged-refresh test to count content hashing as well as reads/parses/model calls.
