## Findings

### 1. Major — production observation cannot recognize a manually removed pane

**`src/integrations/panel/herdr.ts:106–108`** — `observe()` throws for a missing pane instead of returning confirmed absence, making the controller's manual-close/reopen path unreachable with the production adapter.

**Failure scenario:** an open HUD pane is manually closed in herdr; the next automatic open calls `pane.get`, whose error is collapsed by `CliHerdrTransport` into `herdr_transport_unavailable`. Instead of reaching `control.ts:157–159` and recording `closed`, the controller records `uncertain`. Subsequent explicit `/hud on` attempts enter reconciliation and remain uncertain, so the user cannot reopen the panel for that main session. The existing manual-close test hides this mismatch by returning `null` directly from a Map-backed fake.

**Confirmed:** a synthetic Unix-socket server returning a pane-not-found error to the actual `CliPanelHerdr.observe()` produced:

```text
PRODUCTION absent pane throws: herdr_transport_unavailable
AFTER manual pane close {"automatic":true,"diagnostic":"herdr_transport_unavailable","phase":"uncertain","effects":[]}
AFTER manual pane close {"automatic":false,"diagnostic":"herdr_transport_unavailable","phase":"uncertain","effects":[]}
```

**Suggested fix:** distinguish authoritative pane absence from transport/ownership uncertainty, returning `null` only for confirmed absence on the pinned instance. Add a production-adapter/controller test proving automatic suppression followed by successful explicit reopen; do not turn arbitrary transport errors into absence.

### 2. Major — one premature readiness sample permanently strands a successful split

**`src/integrations/panel/control.ts:209–212`** — the controller requires the newly created shell to be ready on its first observation and discards the returned pane identity when it is not.

**Failure scenario:** split succeeds, but the new shell is still initializing or running a foreground command from its rc files. The first observation has `atPrompt: false` (or temporarily unavailable process evidence), so open throws `panel_split_unverified` before assigning `r.panel`. The receipt becomes `uncertain` with `panel: null`; no panel process was started to register, and later calls only look for that nonexistent registration. Even after the shell becomes ready, the empty pane remains stranded. The existing split fake always provides an immediately ready shell. The existing shared herdr host, by contrast, already uses bounded readiness polling.

**Confirmed:** an exact-pane fake changing from not-ready to ready produced:

```text
WHILE shell initializing {"diagnostic":"panel_split_unverified","phase":"uncertain","recordedPane":null,"effects":["split"]}
AFTER shell is ready {"diagnostic":"uncertain","phase":"uncertain","recordedPane":null,"effects":["split"]}
```

**Suggested fix:** retain the known created pane ID and perform bounded readiness observation of that exact pane within the operation deadline, retaining instance/epoch/occupant fencing and never repeating split. Test delayed readiness, transient startup evidence, and expiry/cleanup separately.

### 3. Major — the lost-split-reply state lacks the diagnostic and explicit recovery required by q5

**`src/integrations/panel/control.ts:161–164`**, with the split call at **`:205`** and the misleading test at **`tests/unit/panel-control.test.ts:250–261`** — split-only uncertainty is indistinguishable from other uncertainty and refuses even the explicit fresh attempt authorized by the orchestrator's clarification during this review.

**Clarified boundary:** q5 accepts an empty orphan after a lost split reply; discovering or closing a guessed pane is **not** required. It requires `uncertain` with reason `split_reply_lost`, concise guidance that an empty pane may need manual closing, automatic retries suppressed, and an explicit user open able to start exactly one fresh attempt. Token reconciliation remains required once the pane ID is known.

**Failure scenario:** split creates a pane but its reply times out. The first result reports only `herdr_timeout`; later automatic and explicit opens both return generic `uncertain` with the same generation and no new attempt. There is no actionable orphan-pane diagnostic or explicit recovery path. In addition, the timeout test fabricates a registration for an unstarted shell while `registered: () => true` bypasses production corroboration, so its claimed recovery is impossible through the real registration path.

**Confirmed:** a split-then-timeout fake, with no fabricated registration, returned:

```text
explicit open: uncertain / herdr_timeout / effects=[split]
automatic open: uncertain / uncertain / effects=[split]
explicit open: uncertain / uncertain / effects=[split]
```

All three retained the same generation.

**Suggested fix:** implement q5's distinct lost-split state/diagnostic and explicit-only fresh-generation attempt, leaving the unknown orphan untouched. Replace the fabricated-registration test with separate split-only loss, known-pane run-reply/late-registration reconciliation, and explicit fresh-attempt tests; update the README/report limitation accordingly.
