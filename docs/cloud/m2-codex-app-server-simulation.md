# Codex app-server protocol observation simulation

This slice is a transport-neutral, bounded stdio JSONL observation seam in `src/harness/codex/app-server.ts`. It does not spawn Codex, send a request, authenticate, grant capabilities, handle approval, or integrate with the panel. The caller owns the transport and is responsible for delivering the request objects in order. It is separate from `codex exec --json` and on-disk rollout records.

Pinned source: `openai/codex@d786ff91fad8e7ddab8653ee07bc6313a6fcb03d`, not an installed binary version. The official generated [ClientRequest](https://github.com/openai/codex/blob/d786ff91fad8e7ddab8653ee07bc6313a6fcb03d/codex-rs/app-server-protocol/schema/typescript/ClientRequest.ts), [ServerNotification](https://github.com/openai/codex/blob/d786ff91fad8e7ddab8653ee07bc6313a6fcb03d/codex-rs/app-server-protocol/schema/typescript/ServerNotification.ts), [ThreadStartResponse](https://github.com/openai/codex/blob/d786ff91fad8e7ddab8653ee07bc6313a6fcb03d/codex-rs/app-server-protocol/schema/typescript/v2/ThreadStartResponse.ts), and [InitializeResponse](https://github.com/openai/codex/blob/d786ff91fad8e7ddab8653ee07bc6313a6fcb03d/codex-rs/app-server-protocol/schema/typescript/InitializeResponse.ts) define wire types. The [app-server guide](https://learn.chatgpt.com/docs/app-server) describes the per-connection initialize/initialized handshake and thread start/resume. The rolling guide was read 2026-11-05; it is not the version pin.

The observer matches numeric/string request IDs without conflation, prevents ID reuse per instance, waits for initialization response before producing `initialized`, and checks a resume result's thread ID. Its inbound validation intentionally reads a minimal subset and does not claim full schema validation. Notifications are counted but do not establish thread identity, execution success, or authority. Unsupported server requests are surfaced by ID and method only, without an automatic response or approval. Unknown notification methods are counted; error details and content bodies are not retained. Caller-generated outbound objects and caller-fed input are untrusted assertions, not evidence that a server actually ran.

One observer represents one bounded connection; 64 KiB per line, 4 MiB total and 256 distinct request IDs are defensive implementation limits, not official limits. Newlines frame messages; incomplete EOF, unknown or mismatched response IDs, invalid UTF-8 and invalid shapes report a gap. A terminated/interrupted stream cannot be resumed in the same observer. Request errors are observed separately. Thread IDs are display-only and do not grant managed identity, prove a successful turn, or authenticate any service. No live-client compatibility, full M2 completion, schema-complete handling, reconnect semantics, server-request decisions, or execution of methods beyond the subset is claimed.

Run `npm run build && npm run build:test && node --test dist-test/tests/unit/codex-app-server.test.js` with isolated HOME and HUD_HOME. The tests use only invented frames and values, including byte splitting, interleaved notifications and response IDs, resume mismatch, unknown methods, unsupported approval requests, limits and EOF. They do not need network or accounts.
