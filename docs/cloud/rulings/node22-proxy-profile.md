# Node 22 proxy profile and output compatibility ruling

Date: 2026-11-03.

## Decision

Retain the proxy-enabled Node 22 configuration. Do not replace it with the owner’s separately labeled no-envproxy run. The observed UNDICI-EHPA diagnostic is generated by Node’s startup proxy agent, not by HUD’s SQLite initializer. The two combined-output failures are test-harness stream-mixing defects; the export failures expose an overbroad whole-process stderr expectation and an ambiguous public help promise. No evidence inspected establishes a HUD stdin/argv corruption or proxy-routing implementation defect.

Approve a bounded test-capture/diagnostic-expectation correction and the explicit export-help clarification below. Do not change production proxy routing, suppress the proxy warning, broaden SQLite suppression, or waive a failing matrix. This is a design disposition, not an acceptance verdict. Design is ready; implementation remains HOLD until a complete bounded brief, exact branch/file ownership and an explicit resource window are recorded. Full checks and package acceptance remain open.

The owner delegated project choices to Oracle. This ruling uses that delegation to resolve the public-output wording explicitly, rather than silently weakening assertions or declaring an inconvenient configuration unsupported.

## 2. The supported configuration

The ledger command’s existing runtime predicate remains Node 22.x >=22.13 or Node >=24, excluding Node 23. The cloud verification families remain Node 22 and Node 24. package.json’s broader >=18 declaration does not supersede the ledger command’s explicit runtime check. Do not change those runtime floors in this repair.

Node’s built-in environment-proxy option exists on the Node 22 line from v22.21.0. Thus the automatic-proxy configuration examined here is Node 22.23.4 with NODE_USE_ENV_PROXY=1 set before launch, valid HTTP_PROXY/HTTPS_PROXY or their lowercase equivalents, and the intended NO_PROXY/no_proxy policy. Preserve the configured values and native precedence. ALL_PROXY may be retained for other consumers, but its presence alone is not proof that this Node HTTP/fetch route is enabled. Earlier supported Node 22 releases do not acquire this newer runtime feature merely because the environment variable is present; that is a feature-version distinction, not permission to drop their existing support.

The intended process topology preserves separate stdout and stderr. For headless production, control.ts passes logs.stdout and logs.stderr separately; process.ts transports the selected environment and wires the supplied descriptors without merging them. Contract 04 requires raw-byte logs and exact input transport. Contract 07 makes stdout the export document channel. Neither merging fd 2 into fd 1 and then parsing the result as JSON nor assuming every valid runtime is warning-free is a sound consumer profile.

Node’s --use-env-proxy flag is an equivalent startup option on the relevant runtime, not a warning-free workaround. The owner archive used NODE_USE_ENV_PROXY=1 with NODE_OPTIONS absent. Keep that exact configuration as the required reproduction; do not substitute a different launcher or switch merely to make it quiet.

The no-envproxy matrix retains HTTP(S)_PROXY but omits the opt-in that activates Node’s default proxy handling. Those variables alone do not establish equivalent routing. It is valid additional evidence, but cannot close or replace the enabled profile. The HYG2 Node 24 steps all preceded the recorded proxy-policy change, so they also do not establish a Node 24 envproxy pass.

This ruling promises preservation and correct interpretation of this configuration; it does not claim actual network routing was exercised by the existing offline export/stdin tests, authorize additional outbound data, or promote a harness capability cell.

## 3. Cause and classification

### Runtime warning

Node v22.23.4 pre_execution.js calls setupHttpProxy before the application entry point. When the option is enabled and an HTTP(S) proxy variable exists, it constructs EnvHttpProxyAgent and installs it as the global dispatcher. The bundled constructor emits the UNDICI-EHPA warning once per process. It is a Warning with a distinct code, not the ExperimentalWarning targeted by HYG2’s exact SQLite initialization filter. Both the upstream implementation and the raw archive explain why help, refusal and offline export children receive the warning even without a HUD network request.

Classification: expected runtime diagnostic under the enabled profile. Its visibility is not a new HYG2 production defect. Removing the enabling variable, using no-warnings/disable-warning switches, broadening emitWarning interception or redirecting warnings away to manufacture quiet stderr is not approved.

### Export assertions and the public wording

The HYG2 focused log shows eleven failures. Success cases expect an empty entire stderr; refusal cases expect the HUD reason at byte zero or as the whole stream. The raw differences contain the Node startup warning followed by the expected reason, or the warning alone for successful export. The tested code still emits the intended HUD reason and exit status before the failing stderr assertion. Assertions after the failure did not necessarily execute and are not credited as passing.

The help in src/cli/link-export.ts says failures emit one reason-code line on stderr. Read as a promise about the entire process stream in every supported runtime configuration, that conflicts with HYG2’s requirement to preserve unrelated warnings. I explicitly resolve the boundary in favor of preserving runtime diagnostics and exact application output:

Proposed public wording: “HUD failures emit one reason-code line on stderr and no JSON. Node/runtime diagnostics may also appear on stderr; stdout remains the machine-readable channel.”

This is an explicit clarification of the public output promise and its test interpretation under delegated Oracle authority. It must be recorded and implemented openly. If the old sentence was read as a total-stderr silence guarantee, that reading is being changed; it is not being silently waived. HUD must still emit exactly the same one application reason line, with the same exit status and no partial JSON. Successful exports retain exactly the producer’s stdout bytes. No unrelated warning is hidden, and no unknown extra diagnostic becomes acceptable. This does not amend the separate legacy codex-hud --json compatibility contract or authorize changes to other CLI commands.

Classification: test expectation defect plus a narrow product-documentation ambiguity requiring correction; no demonstrated export serialization defect.

### The two apparent argv/stdin failures

run-process.test.ts:73–74 and run-light-leader.test.ts:102–103 pass the same file descriptor for stdout and stderr. The workload writes its stdin echo/JSON to stdout while Node writes the startup warning to stderr. Their combined file therefore begins with warning bytes and cannot satisfy a pure-echo equality or JSON.parse. The full HYG2 log records those two failures in addition to the eleven export failures.

Classification: test-harness capture defect. It does not establish corruption of fd 0, argv or production’s separately captured stdout. Do not claim all later lifecycle assertions passed in the failed matrix. The remaining proof must come from a corrected capture test that actually reaches them.

## 4. Bounded remedy

1. Keep the entire raw stdout/stderr capture unchanged in evidence. For fresh export children, compare the whole stderr against an explicitly modeled startup diagnostic plus the exact expected HUD diagnostic, or the startup diagnostic alone on success. Retain all exact stdout, exit-code, no-write, database/WAL byte/mtime and refusal assertions.
2. Establish the runtime diagnostic expectation with a minimal no-HUD child under the same pinned binary and declared proxy/warning settings, and the checked upstream behavior. For the observed Node 22.23.4 enabled profile, require the exact known UNDICI-EHPA diagnostic, including the correct child PID/executable-dependent presentation and expected count. Construct expected bytes; never strip or replace bytes in the captured actual stream. No generic Warning regex, arbitrary diagnostic allowance, acceptance of missing required warnings, or expectation learned from the failing HUD child is allowed. An unexpected format/extra warning is an explicit failure to investigate, not silently normalized.
3. Keep the HYG2 fresh-process SQLite negative assertion against raw stderr. Restoring the SQLite notice must still fail. Preserve the existing emitWarning restoration and unrelated-warning positive tests, including the synthetic warning whose text mentions SQLite.
4. Give the two process fixtures distinct output/error descriptors, retaining both files. Compare pure stdout byte-for-byte with the original echo/JSON expectation, and separately assert the expected raw stderr. Keep argv, EOF, helper-exit, scope and cleanup assertions. Add a deterministic workload stderr sentinel so correct separation is tested even on runtimes that do not emit this warning.
5. Clarify only the EXPORT_HELP wording identified above. No production routing or process logic change is justified by this evidence.
6. Add a small synthetic proxy-routing witness on an already permitted executor: explicit proxy-enabled child, controlled loopback proxy/target, exact proxy-hit and NO_PROXY-bypass observations, no real credentials or external destinations. Include the same child environment through launchGroup. A deliberate disabled-opt-in control must not be credited as preserving the route. This proves more than checking the variable’s text. Never modify the user’s live proxy settings or bypass a denied socket/network action.

These are precise assertion/capture corrections, not permission to weaken arbitrary byte assertions. No runtime upgrade, dependency change, package/build-script change, production warning filter, blanket environment sanitization or fixture skip is selected.
