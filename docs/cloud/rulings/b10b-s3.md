**Facts that shape the answers**
1. **Forwarding depends on the mode, not on the key's name** (`tree-page.ts` 1403–1411).
   - With a main pane and no overlay, every key is forwarded raw to Codex.
   - While the panel holds the keys (`⌨ Keys here`), or an overlay is open, nothing is forwarded, and keys the decoder does not name are dropped.
2. **`resumable` is a constant, not a gate.** `details[*].resumable` is one constant written on every node (`tick.ts` 694). `capability_unverified` is the last check in `resumeGate`, after the terminal, slot and conflict checks (`lifecycle.ts` 113).
3. **`put:` keys are positional:** `put:<stack depth>:<row index>` (`rows.ts` 148).
4. **`tree-page.ts` clears the selection before each render.**
   - It reconciles against the empty legacy tree (lines 1016, 1105, 1134).
   - It does not call `renderMonitor` while settings, the activity hub or observability is open.

## Q1 — ⇢ Log / `L`

**Decision.** (A).
- **Which rows.** Every row whose node has a managed run in headless mode (`currentRun.mode = headless`), in any run state: starting, running, cancelling, uncertain, or ended with or without a report.
- **What it does.** ⇢ reads `Log`; `L` or a click emits `delegation-log(key)`.
- **No Log** on visible runs (their ⇢ is Open, enabled or greyed), the root, natives, plain sessions, synthetic `⚠` rows or `⊕N` rows.
- **No-ops.** `L` on any other row, and `o` on a Log row.

**Reason.**
- §3.7 gives active headless runs Log, and §4.9 keeps it after the run ends (`⇢ Log` 仍可看日志). §4.10's Inspector also still lists the log.
- (B) would give a visible row a key whose button says Open.
- (C) contradicts §4.9.
- Whether the log file exists is the dispatcher's question.

**Acceptance.**
- Headless running, uncertain (with ↻ Reconcile), ended with a report, ended without one → ⇢ Log, and `L` → `delegation-log(key)`.
- Visible → ⇢ Open, and `L` → no action.
- Root, native, synthetic `⚠`, `⊕N` → `L` → no action.
- `o` on a Log row → no action.

**Touches.** None. Design-doc wording (non-blocking): §3.7's "活跃 headless" reads as headless, active or ended.

## Q2 — where the selection goes

**Decision.** One rule. The reconcile applies it every frame, and every key uses it:

1. **A destination stays.** A key that is a destination stays selected.
   - Destinations are the plan's rows.
   - In rich, a card's sub-rows past the fifth are not destinations; they live in the card's `+N (…)` line.
   - The summary row and the parent row are not plan rows.
2. **A mapped key follows the map.** A key that `tree.selectionMap` maps (intent → session) continues as the mapped key.
3. **A hidden node goes to its nearest destination ancestor.** This covers a node that is still in the projection but is not a destination: put away, under a collapsed `+N`, or a rich sub-row past the fifth. If its branch was put away into that ancestor's `⊕N` row, the selection goes to the `⊕N` row instead.
4. **A `⊕N` row is identified by its parent, not by its index.**
   - It stays selected while that parent has a `⊕N` row, wherever the row moves.
   - When the parent's `⊕N` row is gone and the parent is hidden, apply rule 3 to the parent.
   - When the parent's `⊕N` row is gone and the parent is shown, take the row now at the old index, clamped. A non-destination there resolves by rule 3. After `a`, that is where its rows came back.
5. **Otherwise** the first destination; with none, null.

**Changes to the default.** Rules 2, 3 and 5 are the implementer's default, accepted, with an additive `parentKey` on `PlannedRow`. The same-index rule for `put:` keys is narrowed to rule 4. One way to build it is a key that holds both parts, such as `put:<index>:<parentKey>`, matched on the parent and rewritten when the index moves.

**Reason.**
- §3.2: "选中跟着节点走而不是跟着行号走".
- A positional key would move the selection onto a neighbouring node whenever a row appeared above it, with no keypress. The next `R` would then act on another run, which §3.7 rules out: "状态变化不能把已选操作换成另一个 run".
- A `⊕N` row has no ⇢ and no ↻, so it is a safe place to park.

**Acceptance.** Brief goal 1, bullets 1, 3 and 4, read as above, plus these tests:
- A selected finished row that is put away → its `⊕N` row.
- A row under a collapsed ancestor → that ancestor.
- A rich sub-row past the fifth → its card.
- A selected `⊕N` row stays selected when a row is inserted above it.
- After `a`, it lands at its old index.
- Its parent put away → the grandparent's `⊕N` row.
- A node gone with no mapping → the first row.

Cost: a hit is one map lookup, memoized with the plan. Ancestor walks run only on a miss (gate #4).

**Touches.** Amends one detail of the standing ruling B10B-s2 Q6 ("the positional `put:` key"). Render-internal.

## Q3 — when ↻ Resume appears

**Decision.**
- **When it appears.** ↻ Resume appears only when all three hold:
  - the node has a managed current run that has ended (`execution.isRunTerminal = true`);
  - that run has a report (`latestReportForRun ≠ null`), of any status;
  - the node has no `reconcile` descriptor (with one, ↻ is Reconcile).
- **Where it never appears.** Rows without a managed run: the root, natives, plain sessions, synthetic `⚠`. Rows whose run has not ended: `✓ / ! · close pane`, and a headless run that has reported but is still alive.
- **In the MVP.** The button is drawn greyed. `R` or a click emits `delegation-diagnostic` with the §5.5 sentence:
  - EN: `resume not verified on this machine · ask the parent to delegate_resume`
  - ZH: `本机 resume 入口未验证 · 请原父调用 delegate_resume`

  It never emits `delegation-copy`.
- **Rejected.** Gating on `resumable.resumable` would make the button unreachable.

**Reason.**
- §3.7 and §4.9 separate when the button appears ("已结束且已报告") from whether it works. For the MVP: "按钮出现但写诊断，不复制"; §4.9: "否则灰".
- Contract 03 sets the link to `reported` for every report status, and §4.10 writes `reported` on `✓` and `!` alike.
- Reconcile wins because `resumeGate` refuses unresolved conflicts.

**Acceptance.**
- Ended, with a report `completed` / `failed` / `blocked` / `interrupted` → greyed ↻ Resume. `R` and a click → `delegation-diagnostic` (EN and ZH), never a copy.
- Ended without a report → no ↻.
- Alive with a report → no ↻.
- Descriptor present → ↻ Reconcile, and `R` → `delegation-copy` carrying the descriptor object as given.

**Touches.** None. Data-layer items (non-blocking, no contract change):
- **(a)** Synthetic `⚠` rows have no `details`, so they get no ↻ Reconcile. The producer must supply a descriptor per conflict relation, for the run of the earliest record.
- **(b)** Once B14 publishes the local resume capability, the view model must carry `resumeGate`'s real result and a resume `ActionDescriptor` (§7 #11).

## Q4 — Switch rows

**Decision.** (A), narrowed. One rule over all cases: a key acts exactly when its button is drawn, and does what a click on that button does. `o` is only Open/Switch; `L` is only Log.

| Row | ⇢ | `o` or click |
|---|---|---|
| Codex native in the viewpoint root's own native subtree (its chain of `edge = native` ancestors reaches the root; exactly the agents the legacy tree lists) | Switch | today's `{type: 'switch', id: identity.ref.sessionId}` |
| Other natives: another harness, or under a delegated session | none | no action (`switchSession` drives the viewpoint's Codex pane) |
| Viewpoint root | none | no action. §3.7 gives it Switch (`⌂`), so the ⌂ button and `m` are unchanged. |
| Visible managed run, Open enabled | Open | `delegation-open(key)` |
| Visible managed run, Open greyed | Open, greyed | no action |
| Plain session | none | no action (its `SurfaceLocator` check is not collected yet) |

(B) is rejected: Switch has a dispatcher today, and routing it through `delegation-open` would leave it dead.

**Acceptance.**
- Native under the root → ⇢ Switch, and `o` → `switch` with `ref.sessionId`.
- Native under a delegated session, or a non-Codex native → no ⇢, and `o` → no action.
- Root → no ⇢, `o` → no action, and `m` / ⌂ unchanged.
- Visible and verified → `delegation-open(key)`.
- Greyed → no action.

**Touches.** None. Open items:
- For the `tree-page.ts` owner (B10D): narrow-pane switching uses `uniquePickerLabel(tree, id)` on the empty legacy tree (line 1201).
- For the data layer: the picker label's inputs for natives.
- For the data layer: the `SurfaceLocator` check for plain sessions (§3.7, §7 #7).

## Q6 — `tree-page.ts`'s reconcile without the view model

**Decision.** (A), accepted. It is sound, and byte-identical when the view model is null, on three conditions:
1. **Setting the flag.** Only `renderMonitor`'s reconcile with a non-null view model writes `delegating: true`. It writes it whenever it reconciled against a view model, whether or not it drew anything (help open, zero size).
2. **Clearing the flag.** With a null view model, `renderMonitor` removes the key before its legacy reconcile. The key is either present or absent, never `false` or `undefined`.
3. **Using the flag.** `reconcileMonitor` without the view model (`tree-page.ts` 1016, 1105, 1134) that sees the flag skips only its selection step. Worktree, file, focus, `revealed` and details-scroll logic run as today.

**Reason.** The flag keeps the selection across the three tree-page calls without touching B10D's file. A session whose view model is always null never gets the key, so its path is today's code. When the view model turns null, the first legacy render clears the flag and falls back as today does for an unknown id.

**Acceptance.**
- A test runs `tree-page.ts`'s order: `reconcileMonitor` without the view model, then `renderMonitor` with it. The selection survives, and the test fails without the flag.
- With a null view model, the state has no `delegating` key and the frames are unchanged.
- When the view model turns null, the selection falls back as in legacy.

**Touches.** None. Follow-up for the `tree-page.ts` owner: pass the view model to those three calls, or stop reconciling the Agents selection there. The flag can then go.

## Q7 — what `n` / `N` jump between

**Decision.**
- **Stops.** A stop is a destination whose own marker has `rank = 0` (§3.2's first bucket): `⚑` (including stop in pane), a live `!`, `⚠` (including synthetic conflict rows), and `?` that is uncertain, supervisor lost, stale or unknown.
- **Excluded.** The viewpoint root's marker. Also never stops: `? not loaded`, `· starting`, `■`, an ended `!`, `✓`.
- **Hidden stops.** A stop that is not a destination is represented by its nearest destination ancestor, so a collapsed row with `pn.sub.rank = 0` is a stop.
- **Movement.** `n` goes to the next stop below the selection in screen order, `N` to the previous; both wrap. No stop → nothing happens. They never unfold, reorder or filter.

**Reason.**
- §2 (e) "排在最前" is rank 0. The marker's `trouble` flag is the row-anatomy property, which includes starting, cancelling and not-loaded rows.
- §3.2: ended failures are "历史事实，不是当前待办".
- §2: "折叠永远带子孙计数，不吞掉深处的求救".

**Acceptance.**
- Each kind of stop, and each excluded kind.
- The root excluded.
- Wrapping in both directions.
- No stops → no action.
- A collapsed row over a `⚑` is a stop and stays collapsed.

**Touches.** None. Design-doc wording (non-blocking): §2's "trouble 节点" means §3.2's first bucket.

## Enter

**Decision.** Enter, Space and `v` stay the Inspector's keys. On a delegation row they keep today's path, opening the details pane on the selection. They emit no delegation action; `o` alone emits Open or Switch.

**Reason.** §2, §4.10 and `docs/reference.md` agree ("Enter, Space, `v` or `◫` opens the Inspector on the selection. `o` and `⌂` switch at once"). §3.7's "`o` / Enter 只做 Open / Switch / Inspector" separates the read-only keys from `R`; it does not make Enter an Open key.

**Acceptance.** Brief goal 4 reads "`o` for Open/Switch". Test: Enter, Space and `v` on a delegation row emit no action.

**Touches.** Brief wording only. Until segment 4, the details pane shows nothing for a delegation key.

## Orchestrator decisions after review 1 (2026-11-03)

  every level except `none`, so §4.9's `⇢ Log` and `⇢ Log ↻ Resume` show at 48 columns. Review 1, finding 3,

    outside it. They must not make their parent, or the root, a stop.
  - Remove the behaviour, and add a test that a parent with only omitted conflicts is not a stop.
- **Below the 32-column floor** (review 1, finding 2). A key acts only when its control is drawn in the frame
  the user saw. Gate `o`/`L`/`R` on the drawn control, not on the bar's condition alone.
